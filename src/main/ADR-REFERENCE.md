- Planned ADR 0455 Text draft recovery is a typed record class inside ADR 0465's trusted-main-process-owned Protected Custom Field Draft Recovery Journal. The complete device-local record must use operating-system protected storage with no plaintext, portable-library, renderer-storage, settings, log, crash-report or plugin fallback; the renderer receives only the bounded recovery projection needed by an exact active library/field flow.
- Planned ADR 0457 Batch Text Edit must execute from one trusted frozen plan with current identity/rule/revision revalidation and per-owner atomic commits. The renderer may request and display bounded projections but must not iterate selected owners, derive authoritative transformations or declare outcomes locally.
- Planned ADR 0458 Batch Text recovery must keep the durable library operation record free of previous Text and stage exact Undo evidence through an OS-protected device-local journal before each item commit. The trusted main process owns reconciliation, storage admission, retention, cross-device terminal markers, Forget/Uninstall disposition and the separately confirmed no-Undo path; it must never auto-resume, clear a non-terminal journal during Forget, infer Cancel Remaining from uninstall, transfer/reconstruct recovery on another device, or expose journal content through renderer storage, backup, sync, plugins, logs or telemetry.
- Planned ADR 0459 Text transfer input must never make HTML/RTF parsing, file/image drops or asset-object display strings an authoritative Text source. Trusted value and Batch Text plan creation still canonicalize and validate the resulting plain Unicode string; clipboard provenance cannot bypass current field rules, and raw transfer content/flavors cannot become logs, telemetry, diagnostics or plugin payload merely because paste/drop occurred.
- Planned ADR 0460 Copy Full Text must resolve the complete current draft-or-authoritative source for the exact field context rather than trusting rendered Compact text. Plain-text clipboard writes reject malformed/unsafe Unicode without alteration, Cut deletes only after write success, and no copy source/content enters history, logs, telemetry, diagnostics, notifications or plugins.
- Planned ADR 0461 writing assistance must classify a checker as local only from capability evidence, not platform branding. Potentially networked system, AI or extension services require a trusted per-request grant scoped to one disclosed selection or complete draft; provider configuration and existing analysis/plugin grants cannot authorize draft reads. Main-process mediation must keep request/result content out of logs, telemetry, diagnostics and portable evidence.
- Planned ADR 0462 Number commits must use one pinned exact parser with the explicitly selected device-local input locale and canonical-conflict detection, never JavaScript/SQLite binary floating point or operating-system guesswork. Trusted validation owns the exact parsed preview, Decimal128/range checks and full-value edit projection; formatted precision/grouping/unit text cannot become a write source.
- Planned ADR 0463 Number formatting must stay in an exact decimal/shared trusted lane rather than converting values through JavaScript Number or a platform formatter. Automatic Exact, fixed-decimal and significant-digit projections use pinned rules; only numerically changed round-half-even results carry approximation state, and no formatted projection can become value, comparison, index, import, migration or edit input.
- Planned ADR 0464 Number projection must compute the 64-grapheme overflow decision and normalized scientific fallback from the same exact decimal result, without a second rounding or formatted-to-number parse. Complete requested formatting is generated only for explicit detail and remains ephemeral; fallback/detail content cannot become value, index, cache, history, log, telemetry or diagnostic evidence.
- Planned ADR 0465 manual Custom Field editing must use one trusted typed draft parent, protected journal infrastructure and current-library session Undo stack across field types. Main-process commit, recovery and Undo revalidate exact owner/field/type/rule/value revisions; Number recovery re-parses the retained literal and input-locale identity instead of trusting stored parser output. No journal plaintext, draft auto-commit, empty-Number-to-zero conversion, cross-type parallel stack or batch/AI/import/migration per-item insertion is allowed.
- Planned ADR 0466 multi-draft resolution must send one complete reviewed plan to trusted main-process validation. Re-resolve and validate every selected Save before any mutation, then commit all selected fields for each owner in one transaction and execute owner groups in frozen order. A later failure keeps proven earlier commits, retains failed/unstarted drafts, removes recovery records only at proven owner boundaries and returns a truthful content-bounded partial result; it must not become a renderer-side loop, global cross-owner transaction or Batch Activity record.
- Planned ADR 0467 compound manual Undo must preserve one same-owner multi-field commit as one indivisible session-stack record containing ordered typed deltas. Trusted Undo/Redo re-resolves every field and commits the complete group in one transaction or none; no renderer-side per-field replay, partial eligibility fallback, type extraction or cross-owner compound step is allowed. Push only proven owner commits in actual order, and evict a compound step only as a whole.
- Planned ADR 0468 unavailable manual Undo must keep the newest ineligible entry blocking until exact trusted revalidation succeeds or the user confirms whole-step removal. Evidence-triggered rechecks are read-only and never use name/value equality, open UI or execute Undo. Removal rechecks, deletes only the still-unavailable in-memory entry plus its Redo state and advances no metadata; no automatic/temporary skip, partial compound removal, bulk removal, persistence, logging or plugin projection is allowed.
- Planned ADR 0469 manual Undo retention must enforce trusted simultaneous whole-step count and conservative retained-byte caps, default 200/64 MiB and device-adjustable only within 20–1,000/8–256 MiB. Admit fitting steps with complete-oldest eviction, never split/pin compound or unavailable entries, and review cap reductions before loss. Oversized owner steps must be detected during zero-write preflight and offer only an in-range cap increase, preserved-draft return or explicit no-Undo save; typed Undo evidence must never spill to disk or borrow protected recovery.
- Planned ADR 0470 Save Without Manual Undo must keep the existing manual stack untouched through confirmation and failed/unproven commits. After the exact no-Undo owner commit is proven, trusted finalization clears all manual Undo and Redo entries before exposing success or accepting another stack command, without a durable/crossable barrier. Multi-owner plans bind each reviewed boundary to the frozen owner order so earlier same-plan steps may be cleared and later recordable commits start a new timeline; operation-scoped Undo remains separate.
- Planned ADR 0471 critical-pressure manual Undo reclamation must require fresh platform-qualified Critical memory evidence after the coordinator has stopped affected background admission and requested safer disposable releases. Trusted main may then evict only oldest complete manual entries in bounded batches with a pressure refresh after each batch; complete Undo/Redo state leaves together, compound/unavailable entries are not split or pinned, and drafts/protected recovery/authoritative writes remain untouched. Renderer/plugin/profile state and Unknown/stale pressure grant no authority, and no private per-entry detail may enter logs, telemetry, activity or plugins.
- Planned ADR 0472 Boolean Inspector commits must accept only explicit True, False or Clear-to-Missing intent bound to exact library/owner/field/type/rule/value revisions. Choosing the current state is a no-op; another choice remains non-authoritative until trusted commit succeeds, then creates one ordinary typed manual Undo with exact prior Boolean-or-Missing state. Failure preserves prior authority and creates neither Undo nor recovery. Never coerce Missing to False, trust localized labels as values, create a draft for the immediate choice or let renderer optimism become commit evidence.
- Planned ADR 0473 Boolean defaults must be optional portable True/False definition state, disabled by default and revision-bound. Apply once only inside authoritative creation of a new Candidate or non-Promotion Design Asset when no explicit import/creation intent exists; explicit Missing also suppresses the default. Promotion transfers Candidate state without reapplication. Default edits never backfill, archive suspends application, reviewed plan drift blocks, and plugins/AI cannot acquire direct default or batch-write authority.
- Planned ADR 0474 Static Custom Field Defaults must reuse each core type's exact authoritative validation/storage representation and remain default-Off, portable definition state. Apply only through the ADR 0473 future-owner/precedence boundary; never backfill or reapply at Promotion. Reject localized/display strings, option labels and every dynamic Today/Now/context/path/user/device/random/AI/plugin/formula/reference input as default authority. Definition proposals may request a static default but host review remains sole schema authority; a later-ineligible retained default cannot be silently coerced or applied.
- Planned ADR 0475 default-invalidating schema/option actions must complete zero-write preflight with a current valid replacement, Disable Default or cancellation; reviewed Select merge is the only stable-identity retarget path. Unexpected migration/upgrade/recovery invalidity preserves exact definition evidence as Suspended and blocks application, not owner creation. Trusted creation writes Missing while attention remains; repair revalidates and affects future owners only. Never create Out-of-Constraint new values, per-owner retries/signals, name remaps, backfill or plugin/AI repair authority.
- Planned ADR 0476 Missing Custom Field Initialization must freeze exact scope generation, owners, fields, typed assignments/default snapshots and all base/schema revisions before confirmation. Write only still-Missing fields, commit all eligible selected fields atomically per owner, and use ordinary batch conflict guards with owner-boundary pause/cancel/recovery. Pre-confirm drift invalidates the plan; post-confirm drift conflicts the whole affected owner group. Persist private active detail only as protected library-bound operation authority, compact terminal history to aggregates, and implement successful-effect-only Undo as current-revision-checked clear-to-Missing without prior-value payload or manual Undo entries.
- Planned ADR 0477 Missing initialization recovery must bind its complete frozen plan, owner checkpoint and effect authority to one exact Local Library Instance, not the initiating device. A compatible device may explicitly Resume, Cancel Remaining or Undo only after Library Open Inspection proves operation compatibility/integrity and exclusive ownership. Never auto-resume; terminalize remaining scope before Undo, and never replay authority into copied/colliding instances or restored backups. Missing, corrupt or unsupported records remain non-authoritative, and this prior-Missing exception must not weaken Batch Text's device-local journal.
- Planned ADR 0478 Missing initialization scope planning must operate on one active Local Library Instance only. Resolve Current Selection from selected current owners, Stable Filter from one complete frozen active-library generation and Library-Wide from all current Active Candidates plus non-deleted Design Assets. Disclose and exclude history, cleanup, Trash and other-library occurrences; do not exclude an active owner merely because source bytes are offline. Invalidate pre-confirm membership drift, conflict post-confirm lifecycle drift per owner, and never follow Promotion Links or substitute restored/new identities.
- Planned ADR 0479 Missing initialization Retry must start only from a terminal reconciled result and explicitly selected Retry-Eligible owner groups with proven transient, wholly uncommitted outcomes. Revalidate the exact library, operation/effect evidence, complete original atomic group, frozen assignments and still-Missing revisions before each attempt. Reclassify Present/drift/ambiguous/recovery cases without writing. Apply the existing three-attempt per-owner limit, merge outcomes into the original result, support compatible cross-device authority under ADR 0477 and provide no automatic or catch-all Retry All path.
- Planned ADR 0480 terminal Missing initialization authority must begin Forward Recovery Open, serialize Retry and Undo, and add every retry success to the potential successful-effect Undo set. Before reversal, trusted preflight must prove terminal exact-library authority; committed Undo direction then closes all remaining forward Retry eligibility durably before the first clear-to-Missing owner commit. Apply the same ordering to Cancel Remaining And Undo Completed. A partial/failed Undo cannot reopen Retry, replay frozen assignments or create Redo; another compatible device observes the same library-bound direction.
- Planned ADR 0481 must freeze one user-configurable, default-30-day Missing Initialization Action Window at first terminal reconciliation. Bind terminal detail, Retry failure evidence, Undo effects and direction to the same exact-library deadline; no action, view, restart, switch or device change extends it. At expiry stop new owner admission, settle/reconcile only the already admitted atomic group and then remove executable detail. Permit Clear Missing Initialization Result And End Actions only when terminal and idle after aggregate disclosure. Preserve current values and at most value-free Pruned Batch Detail.
