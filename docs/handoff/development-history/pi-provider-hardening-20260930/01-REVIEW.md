# Pi 统一模型接入：真实工作区评审

日期：2026-09-30。依据：经 Remote Desktop Commander 读取的当前仓库及已安装 Pi 0.99.1 源码；外部规则单独标注为官方文档核验。

## 1. 评审结论

总体路线合理，建议保留已形成的接入层。现状应表述为“OpenAI-compatible 路径具备原批次隔离证据，多厂商原生调用与订阅存在尚未闭合的集成边界”，而不是“全部 API/订阅已接通，只待用户填账号”。不建议重新设计整个项目，也不建议为了几个 Provider 的差异立刻换掉 Pi。

本次发现的主要共性：统一 SDK 统一了部分数据接口，却没有统一所有 Provider 的网络注入方式、认证前置条件、交互数据和账号副作用。当前测试在 DAM 自己的 Host、凭据补偿、取消和兼容 HTTP 边界上较扎实，在真实上游 Provider 契约上覆盖不足。

## 2. 应保留的设计

- Pi 留在模型传输和认证边界；素材授权、预处理、任务、人工状态和数据库权威仍属于 DAM。
- 独立固定版本 Node 是本次避免同时升级 Electron 与原生依赖的合理增量路线，但要承担额外进程和资源分发成本。
- 凭据独立加密存储、普通配置白名单投影、显式迁移与 revision 补偿，比只隐藏密码框更接近真实安全边界。真实系统保险库尚未验收。
- 业务截断重试仍由 DAM 控制；HTTP/Worker 取消与远端费用停止分开，未知进程占用不以 Promise 拒绝来假装释放。
- 外部细化有独立确认和上游证据关联，当前代码只挑选披露的 caption/prompt/tags，不自动携带历史 OCR。
- 原报告保留失败、真实账号延期与 index 原始摘要无法归因的限制，没有必要把这些诚实记录改写成全部通过。

来源：S01–S09。上述是对代码与报告的判断，不是对所有部署条件的独立验收。

## 3. 发现

### F01 — Google 原生推理必然撞上自定义 fetch 禁止条件

**等级：该 Provider 启用前阻塞。证据：真实已安装 SDK 的限定反例，已运行。**

定位：S04 `worker.mjs` 的 `approvedFetch` 与 `models.stream(... fetch:approvedFetch ...)`；S10 `google-generative-ai.js` 中 `Custom fetch is not supported` 分支。

DAM 对所有 Provider 无条件传入自定义 fetch，用于目的地、重定向、信号和原始响应字节约束。Pi 0.99.1 的 Google 原生适配器在任何 API 请求之前明确拒绝不等于 `globalThis.fetch` 的自定义实现。因此静态模型目录可以返回，真正推理或生成图片能力验证却会失败。

本次在远端系统 Node 25.8.0 中加载实际安装适配器，将网络入口替换为只计数后抛错的函数，得到 `stopReason=error`、明确的自定义 fetch 错误、`networkCalls=0`。这不是捆绑 Node 24.21.0 的完整 Worker 测试，不能伪装成该环境重放；源码中的拒绝条件本身清楚。

**建议：**没有实现同等约束前，将 Google 原生推理标为不可执行。不能仅删除 fetch 参数，让请求脱离现有治理后宣布修复；也不应为了满足引用相等把全局 fetch 随意替换成一段未经完整验证的补丁。选择专用受控传输、符合明确契约的兼容端点，或暂缓该 Provider，逐一验收。

验收：调用真实 Pi Google 适配器；生成输入；禁止真实外发；覆盖合法响应、取消、429 无业务重试、超大响应、重定向和目的地变更；Worker → Host 的保存路径至少一个贯通案例。

### F02 — OpenAI 新 OAuth 缺少 getDeviceId，且需对齐新的账号注册契约

**等级：该登录路径启用前阻塞。证据：源码直接契约检查；本次未执行登录。**

定位：S04 的 `models.login(provider.id,'oauth',interaction)` 只有三个实参；S11 `openai-chatgpt.js` 第185–194行，在登录第一步调用 `options?.getDeviceId?.()` 并对缺失 UUID 抛错；S12 CLI 第65行展示第四参数入口。`lazyOAuth` 只是透传 options，没有生成设备标识的默认实现。

这里是 `providerKind=openai` 的新 ChatGPT 登录，不是 `openai-codex` 的 legacy 路径，也不影响 API Key 模式的相同含义。当前 Worker 缺少该必需参数，不能归因为用户账号没有配置。

**建议：**先确定 DAM 应采用的官方账号接入模式。在应用级保存一次生成、非个人身份信息的稳定 host ID，由 Main 窄接口提供，跨 Worker 和登录复用；不是每次登录 randomUUID，也不使用硬件序列号。

外部核验 W02/W03：当前官方文档提供开源/本地应用使用 ChatGPT plan 的路径，同时要求稳定 host ID、实际应用名、已发行 client ID 的后续复用，以及 ID token 的签名/issuer/audience/expiry/nonce 与返回账号身份验证。已安装 Pi 实现仍有固定 `agent_name_hint=Pi`、每次动态注册和只检查 id_token 存在的行为；这些应记录为固定上游版本与当前集成要求的差距。**补一个 UUID 不等于整个注册与账号验证已经完成。**具体账号/应用是否符合开放条件仍需单独确认，不把文档存在当作自动授权。

验收：先用无网络的真实登录入口契约测试发现缺参；后续使用假授权服务器/令牌完成稳定 ID、取消、错误 state、nonce、账号不匹配、刷新与重登录测试。不得拿真实令牌验证这些故障注入。

### F03 — 旧 Codex 需要 select 选项，但跨进程与 UI 丢失了它们

**等级：正常用户登录流程阻塞。证据：完整静态调用链；本次未运行正式 UI。**

定位：S13 `openai-codex.js` 第324–339行；S04 prompt 序列化；S05 Main prompt 投影；S14 `AiLoginStatus`；S15 `PiConnectionsPanel.tsx` 第36行。

实际 SDK 首先要求选择 Browser login 或 Device code login，并验证返回的选项 ID。Worker 只转发 type/message，Main/契约没有 options，界面把所有 prompt 渲染成密码输入框。普通用户无法从界面看到和选择 SDK 给出的合法选项。手工猜测内部 ID 不是合格产品路径。

**建议：**使用受限鉴别联合契约表示 text、secret、manual_code、select，保留经校验的选项 id/label、长度和数量限制。Main 校验答案必须属于当前 operation/prompt 的允许选项；旧登录答案不能投给新操作。secret 仍不可回读。不是把 SDK 任意对象原样穿透到 Renderer。

验收：用真实固定 Codex OAuth 入口触发首个 select；完整 Worker → Main → React 展示与答案传回；覆盖两种分支、非法 ID、过期 prompt、取消和 A→B→A 操作代次。

### F04 — Anthropic SDK 的 OAuth 支持不等于 DAM 可以提供 Claude 订阅登录

**等级：产品开放前的厂商政策门槛。证据：源码配置 + 2026-09-30 官方文档核验。**

定位：S16 `PI_PROVIDER_AUTH_MODES` 将 anthropic 的 api-key/oauth 都列为可用；S15 据此显示登录；S05 允许该 Provider 发起登录并保管令牌。

W01 当前官方条款明确区分第三方自己的应用与未经修改的 Claude Code：第三方产品应使用 API key/支持的云渠道，不允许在自己的应用内提供 Claude.ai 登录或代用户路由 Free/Pro/Max 凭据。原样托管官方 Claude Code 的例外不是 Pi Worker 直连的自动依据。

**建议：**DAM 标准配置禁用 Anthropic 订阅 OAuth，保留 API Key；Main 与 UI 同时限制，已有记录采取明确不执行/迁移提示，不未经确认删除用户数据。存在具体书面例外时按该范围另行核验。不要因为其他 SDK 列出按钮，就把它加入正常可执行矩阵。

这项不能泛化为“所有厂商订阅都禁止第三方”。W02/W03 对 OpenAI 的当前路径另有说明；每家分别判断。

### F05 — Copilot 登录可能修改账号模型策略，不只是取得令牌

**等级：账号登录开放前需收敛。证据：已安装上游源码分支；未触发真实账号。**

定位：S17 `github-copilot.js` 的 `loginGitHubCopilot`、`enableGitHubCopilotModels` 和 `enableGitHubCopilotModel`。

当模型目录包含 policy 未配置项目时，当前 SDK 登录会进一步 POST `/models/<id>/policy`，请求 `state=enabled`。界面的通用“开始订阅登录”并没有对应的逐项审阅。它不是每次必然发生，也没有证据表明本次曾修改任何真实账号。

**建议：**登录、模型目录和账号配置写入分开授权；缺少显式许可时不得自动启用账号模型策略。无法控制固定 SDK 的该副作用时先不开放这一路径，或经上游支持/窄适配后再验收。企业域名及账号派生端点也必须在发生网络动作前匹配授权目标，不能只在末尾保存凭据时才检查。

验收：真实 OAuth 适配器 + 合成设备码/目录/策略服务器；无额外授权时策略 POST 为零；有授权时仅指定条目，拒绝多写、重定向及未披露域名。

### F06 — 推理的受控 fetch 没有自动覆盖认证、刷新与账号目录

**等级：认证网络专项验收项。证据：静态路径；未证明实际泄露。**

定位：S04 先 `models.getAuth` 后才创建 approvedFetch；S11/S17 认证模块自行调用 fetch、response.json/text。推理的 `maxRetries=0` 也不会自动重写登录模块内部的重试/轮询规则。

因此不能把“推理受限”写成“所有请求都具有同一目的地、响应体和重定向限制”。当前外层5分钟和终止子进程仍有价值，但不是原始认证响应的字节上限证明。

**建议：**为推理、认证、刷新、模型目录和账号写入分别列出允许目的地/方法、响应字节、重试与轮询预算，验证实际调用路径。授权服务器与模型 API 可以是不同域，不应机械强制相同 origin。错误与日志继续只返回安全分类，不回传上游正文或令牌。

### OBS01 — 每次调用全量扫描和哈希 Runtime 的长期成本

**等级：性能/维护设计观察，不作为当前数值性能结论。证据：生产代码 + 原报告记录，未实测。**

定位：S06 `execute()` 每次 `await verify()`；verify 递归扫描 node_modules/runtime 并逐文件读取及哈希。原报告记录11827个普通文件和2个链接，**本次未独立重数这些条目**。

这堵住了上游复核找到的未封印依赖遮蔽问题，不能删掉保护。但对多素材后台任务，每次重新遍历整个执行环境、再创建 Worker，会增加与模型计算无关的开销。verify 内部没有 signal 检查，取消只在前后观察，长校验也会影响取消响应。

建议先测冷/热校验、单素材与批次、取消延迟、文件读取量；再比较受保护的不可变版本目录、共享可取消验证任务、证据缓存及明确失效条件。不能以缓存收益为由接受可变未验证依赖，也不需要现在上完整常驻服务。修改 Worker 或依赖须重新封印和重验。

## 4. 测试评价

原报告记载43项新增、130项回归和最终独立复跑10项。本次阅读报告与选定测试源码，没有整套复跑，也没有对这些计数做完整日志摘要审计。

`pi-runtime.test.ts` 的5项和 `pi-visual.integration.test.ts` 的7项主要通过 openai-compatible 的自有 SSE 服务验证实际 Pi/Host；这证明兼容路径与保存边界，但不能替代 Google、OpenAI Responses、Anthropic、Codex、Copilot 原生 adapter 各自的契约。

`pi-oauth.test.ts` 9项主要使用合成 child 消息或替换 Runtime，善于验证凭据延迟提交、失败保留、UNKNOWN与Main操作作用域，但没有让实际 SDK 的首个 select/getDeviceId 前置条件穿过全链。

建议采用“Provider × 认证模式 × 动作”的最小矩阵，而不是盲目增加总测试数。正常响应、超大响应、取消、429重试、OAuth 首次/刷新/登出、账户副作用，每个支持路径须能指向实际适配器测试。真实账号可按用户选择继续延期；无账号不是不能做上述离线契约测试的理由。

## 5. 对总框架的影响

Pi 是多模型调用/认证适配层，不是本地 GPU 推理引擎，也不替代资源Governor。继续保留：

DAM 能力/任务/外发授权 → Gateway → Provider专属传输与认证 → Pi/现有本地HTTP → Host结果。

仅建议补足几项可判定元数据：SDK技术支持、产品允许、离线契约通过、真实服务已验、当前账号/模型/目的地有效。普通模式只开放具备所需证据的组合；高级模式不绕过权限与厂商政策。此处不要求新增一套巨大注册中心。
