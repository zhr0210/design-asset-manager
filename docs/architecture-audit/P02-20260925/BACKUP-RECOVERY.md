# P02｜备份、验证与恢复边界

状态：Proposed。当前未创建/读取/复制任何真实或临时SQLite、Original、预览或模型文件。下面描述待验证方案。

## 1. 三种制品分开

| 制品 | 覆盖 | 不保证 |
| --- | --- | --- |
| 一致SQLite备份 | schema、控制身份、素材元数据/用户内容/结果与库内日志 | Original、预览、下载块、staging实际字节仍在 |
| 原件/派生/恢复文件备份或清单 | 被明确授权的具体文件集合、归属和状态 | 单纯清单不等于文件字节已经备份 |
| 操作/恢复记录 | 迁移ID、定义digest、source/target profile、备份状态及检查点 | 日志phase不证明DB提交、持久授权或所有文件都恢复 |

数据库备份本身含用户元数据，是私有材料，应保存在受控本地目的地，不进入聊天、仓库或默认远程上传。公开报告只用opaque backup identity/状态，不暴露内容、原件路径或密钥。

## 2. 一致性数据库备份

S22描述在线备份可在成功完成后形成一致DB快照。拟复用锁定better-sqlite3 12.10.0的`db.backup(destination)`，从Host持有的源连接发起；目的地由Main在获准受控位置分配唯一文件，不接受Renderer任意路径，不覆盖已有备份或源库。

目标顺序：停新写准入并收敛→核验源/目的地归属→备份到未发布文件→等待完成→关闭目的连接/确认无未收敛写→校验→受控发布与同步记录→允许DDL。备份中止、空间不足、摘要或检查不合格均不能继续迁移。

运行库可能在备份期间变化，因此“调用backup时的某一毫秒”不是未经控制就能承诺的基线。目标通过暂停DAM写入、持有lease和前后修改证据核验锁定本次迁移前状态；第三方绕过DAM锁的写入需检测并使计划失效。

校验至少包括：预期大小/字节摘要、只读打开成功、quick_check/integrity_check结果、foreign_key_check、application_id、库/lineage/control身份、源版本精确profile，以及合成回归中用户数据/组织/引用保持。只看备份文件存在或backup Promise成功不等于所有这些校验已通过。

不在`db.transaction(async () => …)`里await备份。备份是事务外异步阶段，DDL和必要的首条业务写是事务内同步阶段。是否使用immediate事务及等待预算由对应平台隔离测试决定，不在SPEC假设已验证。

## 3. WAL与当前DELETE模式

当前Managed库是DELETE模式；本阶段不转换为WAL。遇到-journal/-wal/-shm时，当前普通opener会拒绝。

S23表明WAL可能包含已提交事务，仅复制活动主数据库会遗漏状态；不能手动删sidecar后重新打开，也不能把活动主文件直接同步当多端协议。本轮只将这些列为负向/恢复场景，不尝试打开或checkpoint真实有sidecar的库。

若后续需要处理损坏或热日志，必须通过另行批准的受控副本/恢复工具验证，保留原现场；不改变普通打开的fail-closed边界。

## 4. 文件覆盖与半完成操作

纯DDL升级不改Original/Preview。其DB备份可明确标`database-only`；若用户需要灾难恢复的全库备份，要另行选择并验证文件字节范围。备份清单不得因为有路径条目就标bytes-backed-up。

下载checkpoint、variant staging、已发布但未关联的文件有独立身份和摘要，不能只备份数据库后假设可重建所有文件。迁移期间冻结相关写入，记录owned references及覆盖状态；未知文件保留，不猜测归属、不自动垃圾回收。

例：副本staging已写，登记意图的DB事务失败。DB可以回滚，但文件可能仍存在；记录需区分“源schema未变”和“存在未关联的owned staging”。不自动清空目录，也不把副本标为完成。

## 5. 崩溃/取消检查点

| 时点 | 后续处理 |
| --- | --- |
| 未确认 | 只有读取计划，不产生备份/DDL |
| 备份进行中 | 取消仅中止本次owned备份；源库不迁移；部分文件保持待核对 |
| 备份验证完成，DDL未开始 | 原库应仍为源profile；重启后新授权、新计划，不能复用旧receipt |
| DDL事务失败且回滚证实 | 重新验证源profile/数据，不手工降低版本 |
| 崩溃留sidecar | 普通打开拒绝；进入明确恢复流程，而非直接删除或强开 |
| DB已commit，记录/通知没完成 | 先检查目标profile和领域回执；未明就OutcomeUnknown，不重放、不自动还原 |
| 后验失败 | 停止写准入，保留当前DB、备份与记录；不得将部分状态报ready |
| 已升级后又有用户修改 | 旧备份恢复会丢后续数据，必须披露并获准；默认保留现状 |

## 6. 三类回退

- **代码入口回退**：关闭新编排入口，回到保留的旧调用路径；前提是该二进制支持当前精确schema。不是修改user_version。
- **索引重建/代际回退**：仅对可重建投影适用；不得删除用户确认标签/OCR修订等原始事实。本阶段未新增FTS/向量索引。
- **数据库/文件恢复**：从验证备份恢复到新隔离目标，先核对DB及文件覆盖，再经授权切换活动库；原库保留。原地替换、处理既有identity冲突等需具体恢复计划与范围批准。

恢复后不能把备份中的运行generation/旧receipt或exclusive lock DB当成活跃权限。重新取得有效会话/lease，撤销旧窗口和任务执行权。来源库和目标库不能同时以同一可写身份活动。

## 7. 验证与待决

本轮备份API、fsync发布、损坏恢复、跨平台、断电持久性与恢复后重开均NOT_RUN。备份目标选择/空间预估/保留策略/记录位置尚未批准。正式实施前需在临时库完成对应故障测试，真实用户库迁移继续单独授权。
