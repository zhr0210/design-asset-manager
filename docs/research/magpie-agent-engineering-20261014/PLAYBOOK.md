# 可学习复用的自动化编程手册

本手册把 Magpie 的实际项目规则与事故整理成通用方法。**案例事实**取自固定仓库快照；**迁移建议**是本报告提出的做法，未在 DAM 实施。本轮不创建定时任务、不发送社区消息、不修改产品治理、不合并或发布代码。

## 一、先理解闭环的七个部分

| 部分 | 必须回答的问题 | 产出 |
| --- | --- | --- |
| 观察 | 什么变化值得触发工作？ | 新反馈与状态变化 |
| 分流 | 是 bug、需求、使用问题、重复还是无关？ | 有依据的分类 |
| 决策 | 符合目标吗？是否有保留给人的选择？ | 做/不做/待定及原因 |
| 执行 | 问题能否在目标环境复现，修复怎样到达用户？ | 独立候选与复现证据 |
| 审查 | 修复前会失败吗？相反错误也能抓住吗？ | 行为验证与范围检查 |
| 交付 | 测过的是即将交付的版本吗？产物真的存在吗？ | 发布/安装/用户确认记录 |
| 学习 | 返工因为什么，下一次何时如何检查？ | 可执行经验与回归要求 |

调度器负责再次触发；规则和验证负责判断正确；状态记录负责避免重复；人负责被保留的决策。只有最后一步改变了下一次行为，才形成学习。

## 二、项目约束文件应该怎样写

### 1. AGENTS 写入口、边界与高频规则

不要把所有历史塞进 AGENTS。告诉 Agent 当前任务应去哪份权威资料、有哪些不可擅自改变的承诺、普通入口怎样验证、什么情况需要人介入。模块细节放在所属文档，重复事故保留在经验档案。

Magpie 的入口最初承担路由职责，当前也加入了插件移交的实际路径判断，这是一个重要例外：如果反复修错运行归属，把判断线索放在入口有价值。不是为了短而删除 Agent 必须先知道的事实。

### 2. 子系统文档写实际运行契约

记录职责和边界、状态权威、主要调用链、转换条件、失败和兼容性、验证入口，并指向真实代码。说明触发条件下用户行为如何变化。内部重构不改变契约时，不必追加大量日志；改变契约时，在同一变更更新权威说明。

Magpie 的插件移交就是例子：已经移交的用户由插件处理登录、模型、请求与错误。修旧内置代码的测试即使通过，也不能证明移交用户得到修复。

### 3. 产品决定写目标、原因和替代范围

保存“为何不采用某方案”“哪项偏好已确认”“什么决定仍可调整”。不要只保存一张截图或一句禁止。重大转向明确替代哪项旧决定，而不是让 Agent 一边读到旧规则，一边猜测是否可以违反。

### 4. LESSONS 写可执行规则与反例

最少包括触发条件、应做动作、错误后果、证据、验证方法、出现日期。记录正例，让后续 Agent 知道正确做法长什么样。没有新证据就不增加 Seen；三个渠道的重复报告合并为一个事件。

### 5. Code standards 写可审查的完成条件

例如“测试质量要高”太抽象。更可执行的是：恢复旧实现时，新测试在运行阶段报出用户行为错误；故意破坏允许与拒绝两侧，测试分别失败；恢复修复后再通过。

能机械检查的稳定规则，可以进入工具或 CI；仍需产品判断的条款保留审查职责。不要通过扩大规则数量制造一种虚假确定感。

## 四、Magpie 的六项验收转换成通用检查

以下是规范结构的迁移，不要求所有项目照抄 Go 命令或平台数。

1. **修复是否被证明必要？** 旧实现/被破坏的保证会让新验证失败，正确实现通过。测试描述的是外部行为。
2. **验证是否隔离？** 模拟/故障注入在可恢复副本中；不触碰唯一资料、账号与生产配置。账号可由应用既有安全机制使用，Agent 只看非敏感结果。
3. **构建与受影响消费者是否覆盖？** 从最小相关检查开始，再按已知跨模块约束扩大。Magpie 因跨包 guard 要求最终 Go 全套；其他项目应按自己的调用链和风险选择，不能把只测改动文件当完整性证据。
4. **界面是否覆盖真实呈现条件？** 相关引擎、语言、窗口/设备、布局与状态。共享 UI 与原生宿主分别验证。
5. **真实服务/平台是否可用？** 改动适用时，经授权在真实目标客户端/服务验证；缺环境就注明，不能用 fake 冒称真实通过，也不冻结无关功能。
6. **产品决定是否保持？** 已确认的交互、视觉与兼容语义不被擅自改变；必要改变由有权人确定。

Magpie 当前 Go 全套仍没有 Windows 通用全量运行，GUI 也不在 test CI 中。因此执行报告需要分层，不写含糊的“三端全绿”。

## 五、建议复用的最小任务状态

这是新增建议，未证明作者已有同样状态机。

`发现 → 已分类 → 待决定/已认领 → 已复现 → 候选待审 → 验证完成 → 待交付 → 已交付待确认 → 已解决`

另有：`重复关联`、`不计划且已解释`、`缺资料/环境`、`失败待处理`、`取消`。遇到用户说先别做，立即以当前明确指令更新任务；不要因为任务曾获准就忽略后来撤回。

每项至少记录：统一 id、来源链接、目标、当前版本、环境、复现、所有者、当前状态、候选 SHA、检查证据、未执行项、实际产物、用户确认。不同渠道报告同一个问题，链接到一个 id；一条负责实现，另外两条补证据和通知。

## 六、三条循环的学习模板

下面是**本报告重新设计的模板**，不是作者原文。没有工具接入、明确授权和运行环境时，只产出可审查的任务记录；不自动扩大权限。执行频率应按新事件、噪声、预算和验证速度选择。

### 循环 A：发现与分流

```text
查看已授权来源的新事件和既有任务的状态变化。
先按统一任务 id 去重，区分 bug、需求、使用问题、无关内容和广告。
读完最新回复，保存用户目标、复现条件、已确认与仍待决定事项。
按产品目标判断价值；保留给人的取舍写成具体选项及影响。
对值得处理的问题标记责任人与下一步；已有人认领则补证据。
未经本次会话授权，不对外发消息、关闭 Issue 或承诺发布。
没有变化就结束本轮；不要为了本轮产出制造新任务。
```

### 循环 B：实现与独立验证

```text
从已认领任务选择一项，在独立工作副本中工作。
阅读相关权威资料，核对实际运行路径和目标版本。
先用用户实际入口复现，再定位根因和同类消费者。
实现达到目标所需的变更，保持用户数据与已确认产品决定。
验证新检查能抓住旧错误；对重要保证做适当的反向破坏检查。
从最小相关测试开始，按平台、状态、并发和消费者风险扩大。
完成适用的真实用户路径，列出缺环境、未运行与失败的部分。
提交待审候选和证据；未有合并/发布授权则停在可审查结果。
```

### 循环 C：质量复盘

```text
检查本轮新增的提交、失败、返工、回滚和用户再次报告。
只依据具体事件，找出错误读题、修复遗漏、弱验证、错误合并和交付失败。
区分同一事故的重复消息与不同日期的新事故；维护 Seen 日期集合。
每条经验必须有触发条件、动作、原因、证据和能发现问题的验证方法。
补做对的例子，合并重复条目，移除已被明确替代的错误规则。
高风险问题立即升级；普通重复经验可在三个不同日期后申请提升为规范。
能自动判定的稳定要求提议进入工具；不能仅因复盘次数多而自动改产品政策。
问题没有人负责时，明确认领或具体交接，不只再写一句发现了。
本轮没有新证据就结束，不进行无限重构、盲目清理或自动封禁用户。
```

不要求三个角色同时写同一目录。初期可以由一个 Agent 串行运行流程，再用独立候选增加并行；这样更容易验证每个环节是否真正消费了上一环节的结果。

## 七、可复制的记录模板

### 经验条目

```markdown
### L-001：读取失败必须保留未知状态
适用：读取结果用于写入、权限判断或幂等判断。
动作：返回可观察的未知/错误；保留原内容；禁止当空值写回。
原因：将损坏读成空值可能覆盖数据或重复执行。
事件：Issue/提交、目标版本、平台、用户后果。
验证：注入不可读/解析失败；确认旧状态保留且副作用不发生。
正例：已验证的修复和证据。
Seen dates：不同复盘日期集合。
最后命中：日期。
状态：经验 / 待提升 / 已纳入规范 / 被明确替代。
```

“出现三天再提升”适合识别反复工程习惯。涉及不可逆数据损失、越权、隐私或严重安全问题不应等待三次事故。90 天没有命中也不自动删除高风险保护。

### 验证与交付记录

```markdown
目标与用户入口：
旧行为 → 新行为：
运行身份：系统、客户端、版本、环境/资料范围。
被测候选：完整 SHA 或产物哈希。
复现：原始步骤与结果。
修复必要性：旧实现为何失败；恢复后为何通过。
同类入口与相邻保持项：
执行检查：命令/操作、结果、证据位置。
真实路径：入口 → 执行 → 结果 → 保存/重开（适用时）。
失败/取消/恢复：
未运行、阻碍、已知失败：
最终交付：版本、实际产物、安装/入口、用户确认。
```

### 人工介入触发条件

```text
产品目标或已确认决定需要改变；兼容承诺可能破坏；
唯一资料不可逆影响；新的隐私披露/服务/费用范围；
外部代码触及工作流、发布、凭据或不相关网络；
合理假设无法由当前可授权检查区分；反复修复仍无法完成真实目标；
需要对外合并、发布或代表用户沟通且尚未授权。
```

介入请求要带可审查结果、选项、影响和具体缺口。一般内部代码修改、可逆验证与已授权范围不逐步询问。

## 八、逐步学习而不是一次搭大平台

| 步骤 | 学习练习 | 达到什么才扩大 |
| --- | --- | --- |
| 1 | 选一个已授权的小 bug，写入口和预期 | 能可靠复现，知道何时算结束 |
| 2 | 找到运行路径和状态权威 | 可解释修复怎样到达用户 |
| 3 | 做修复必要性检查与相邻保持检查 | 测试不是镜像实现或假通过 |
| 4 | 跑正式客户端的完整适用路径 | 能区分内部通过与用户通过 |
| 5 | 保存提交/产物与证据，等待确认 | 交付不再靠一句已修好 |
| 6 | 对一次返工写经验并用于下一任务 | 下一任务实际执行该检查 |
| 7 | 加只读反馈分流与去重 | 有新任务才唤醒执行、没有变化不制造噪声 |
| 8 | 增加独立工作副本和单一合并责任 | 并行提高有效吞吐而非返工 |
| 9 | 将稳定要求落实到检查工具 | 工具能准确发现违规，不降低正确标准 |

不要用强行七天的日程替代里程碑。一个步骤没有真实证据，继续堆调度和角色只会加速不确定性。

## 九、怎样衡量复用是否有效

| 指标 | 建议定义 |
| --- | --- |
| 一次修复成功率 | 在设定观察期内没有因同一目标返工、且用户确认的修复 / 已交付修复 |
| 同类复发 | 已知事故类型在新任务中再次发生的次数；重复渠道报告去重 |
| 验证覆盖完整率 | 实际执行的适用检查 / 任务应执行的检查；另列未执行原因 |
| 用户结果周期 | 从有效报告到真实确认，不只到提交或合并 |
| 返工成本 | 同一任务额外运行、修补、审查与人工时间 |
| 单个有效结果成本 | Agent、服务、环境费用加人工时间 / 已确认结果 |
| 交付失败率 | tag/发布请求未产出完整可用版本的比例 |
| 重复工作 | 同一任务多路认领、重复提交、相互覆盖的次数 |
| 体验负担 | 更新提示、配置丢失、回滚困难、功能膨胀、用户投诉 |

不用提交数、版本数、星数、测试数量单独判断成功，也不用未经验证的“零故障/十倍效率”描述效果。

## 十、放到 DAM 时怎样保留已有上下文

这是讨论层面的映射，没有改动 DAM 的权威文档或创建实施任务。

- AGENTS 已有按任务读取、一个副本一个写入者、保护 WIP、正式入口验收等要求，不应另造一份冲突的通用规则。
- 产品目标、设计、交互、架构、当前状态、验收证据按现有职责放回各自权威入口；外部案例报告不能变成 DESIGN 或 CURRENT-STATE 的当前事实。
- 用案例反推检查：用户真实路径、失败读取保留未知、Managed Copy 与用户编辑语义、取消/幂等、Host 权威、原生窗口、实际运行 profile。
- 经验档案可以作为研究材料，但若要纳入开发规则，应明确哪类现有问题需要它、谁消费、如何检验实际生效。
- 保留 DAM 的资料与凭据边界。Magpie 原规范有复制凭据到隔离环境的表述；它不覆盖 DAM 禁止 Agent 读取秘密的保护。真实应用通过已有机制内部使用账号，Agent 只看非敏感结果。

本研究到可学习资料为止；后续若要实施，再围绕具体用户结果确定范围。
