## 问题与经验的区别

工作约定：问题记录表达一项具体偏差及其当前处理状态；经验表达在一类条件下应执行的检查或动作。一次用户投诉不是一条全局禁令；一个测试失败也不自动等同产品 bug。

问题至少区分产品行为、测试夹具、环境/工具、证据缺口和待核实报告。未执行记未执行，尚未复现记待核实；文档记录不能自行转成当前事实。

## 每次任务怎样执行

1. **定结果与范围。** 明确用户入口、预期、失败分支、候选、资料和服务边界。
2. **读相关资料。** 复用现有上下文路由；检查相关未解决问题和经验，不把整个历史队列加载成任务。
3. **验证记录适用。** 核对当前代码、实际调用者和最新用户要求；将适用经验列为本次具体检查。
4. **执行与验证。** 在获批目标内自主处理必要相邻问题，按风险扩大检查；修夹具不降低正确验收标准。
5. **写回结果。** 更新本任务处理的问题、验收证据与实际能力；不相关发现只登记，不自动扩大实施目标。
6. **提炼经验。** 根据具体原因记录可执行教训与有效正例；合并重复事件，不按留言数虚增次数。
7. **结束与交接。** 用户目标完成后停止；未解决项写清事实、依赖条件与下一检查，保留给后续适用任务。

## 经验怎样影响规范

- 有因果证据的经验可立即记录，不要求等第三次才学习。
- 反复出现的同类问题可成为规范或机械检查的候选；不机械照抄“三天”或“90 天”的门槛。
- 高风险数据、权限和安全保护不等待多次事故；沿用已确认保护并补相关检查。
- 纯工程规则的修正可在获批目标内落实；涉及产品目标、视觉取舍、兼容承诺或新资料/费用范围，保留相应用户决定。
- 规范提升要说明哪项检查会执行它。只增加文字而没有消费者，不算闭环生效。

- 对一个具体任务，相关问题和经验能被现有入口找到；不相关记录不会被强制加入范围。

### 子系统说明如何进入闭环

索引回答去哪找，模块说明回答谁拥有状态和运行路径，实际代码回答现在是否真的这样运行。不能只按文件夹找到一个 README 就认为链路已核对。

例如素材检索同时涉及 asset-search、retrieval-workspace、共享 Client、Renderer 查询会话与 Store。修改查询接口后，相关键盘/分页消费者和测试夹具应一起核对。问题记录链接这些模块与证据；经验说明下一次改变接口时要检查什么。

模块 README 保持当前机制，交互规格保持用户契约，历史失败留检查点，已交付资格归 CURRENT-STATE。发现局部说明与当前代码冲突时修正对应权威入口，不复制一份全新描述来绕过冲突。

### contributors 的适配范围

Magpie 要面对公开社区 PR、重复低价值作者和恶意贡献。DAM 当前主要是所有者委托 AI 工作，因此保留有用的变更审查原则：目的与完整 diff 相符、核对实际调用链、独立检查验证声明、保留用户内容、保护候选与 WIP，以及检查新增外发/发布权限是否在目标范围内。

不复制对作者封禁、广告回复或每条外部 PR 都暂停的流程。既有工程自主权仍有效：必要内部代码、依赖、schema和测试由实施者处理；改变产品目标、资料/费用范围、唯一原件或对外发布仍按现有边界办理。

未来出现外部贡献者后，再扩展 CONTRIBUTING 的相应职责，避免无消费者的独立 contributors 文件。

### test 的适配范围

当前 cross-platform-governance.yml 已有 pull_request、main push与手动触发，执行 npm ci、类型、构建、ci:governance，矩阵为 Windows/macOS。它显式禁用模型/Runtime下载、真实 AI Worker和外部推理。这些检查不能证明真实模型质量和原生用户路径。

上述是现有 CI 的静态事实，不是新真实验收的执行限制。按用户最新要求，正式真实验收使用现有模型、真实 Worker 和适用外部推理；保留不下载模型的约束，不因普通 CI 禁用开关而跳过真实推理，也不简单在所有公共/远端检查中放开真实服务。缺现有模型或资格时，只登记依赖该模型的缺口，不能自动下载、补齐权重或换一个未获采用的模型来求通过。已明确资料、服务和费用范围内持续复验，应用内部使用账号，Agent只看非敏感结果。

闭源不阻止已有私有开发 CI；本闭环优先保持本地可执行，不要求将反馈或新源码推送到远端。源代码、候选和实际运行身份要绑定，不能拿旧远端绿色记录证明未推送的本地变更。

拟将执行报告关联到本地问题：失败保留检查名称、候选、实际错误、归因状态、下一验证；红项不因重跑变绿就抹掉。涉及跨模块保护或打包时扩大覆盖，日常不每次强制整套长链检查。

### UI preview 的适配范围

Magpie 的 workflow 把候选构建与录屏产物发布分开，值得学习的是可审查的实际画面及版本绑定。其工作流还让候选代码接触低额度模型 key；DAM 不继承这种权限安排。

拟议的本地预览应：

1. 固定独立候选和明确的测试 profile，核对实际构建号、客户端和资料范围。
2. 从正式可发现入口操作，不通过隐藏 route、IPC、Store 注入绕过用户步骤。
3. 用非隐私合成材料对照视觉，用已指定公共材料另验正式数据链路；两种证据分开。
4. 输出改动前后截图、必要连续帧/录屏、实际步骤和状态，关联问题 id。
5. 共享浏览器验证负责共享 UI；原生窗口、文件交接、系统选择器、保存重开按目标平台验证。
6. 无录屏或原生工具时保留缺口，不把静态截图当动画通过。

7. 每次任何实现改动影响 UI/UX，都按受影响路径检查，包括后端改动导致的等待、错误、数据呈现和恢复变化。视觉规范来自根 DESIGN.md，功能行为来自其指向的交互规格；新 UI 功能按目标状态验证，缺陷修复还必须复现原问题并用运行/代码证据验证根因和修复效果。
8. 无法复现、仅看到页面能打开、换环境后没再出现、禁用路径绕过问题，都不能作为该问题 PASS。按实际缺口记录待复现、NOT_RUN 或 BLOCKED_UX_ACCEPTANCE。独立检查的限定成功可以保留，但不能关闭尚未证明解决的问题。截图是证据之一，不是完成判据。

预览便于审查，不自动等于验收完成，更不自动托管网页、上传截图或代表用户发 PR 评论。既有资料保护和唯一 Host 继续有效。

### Docker 与候选校验的适配范围

Magpie 的 docker.yml 既检查镜像，也向 registry 发布镜像，因为它有真实服务器/NAS产品消费者。DAM 的本机 Browser 仍依赖唯一 Electron Host，不因有网页客户端就成为容器服务器产品。

Linux容器可用于有具体需求的纯逻辑/依赖隔离，不证明 Mac 的 AppKit、Keychain、拖出、窗口合成或 Windows 原生文件行为。当前不建立容器化产品或镜像发布队列。

已核对 `scripts/verify-local-candidate.mjs` 启动时要求 win32/x64；`verify-candidate-source.mjs` 只验证便携源码字节，不验证运行环境、UI或模型。因此 Mac 预览/资格不能直接复用这两项为完整证明，应复用当前适用的 macOS 构建身份/包证据，并在消费者确实需要时补其对应校验。

### npm 命令怎样承担 Makefile 职责

已有 typecheck、build、context:route/context:check、design:check、ci:governance、start:desktop/start:browser 等入口。它们是实际执行链，模块说明只引用，不抄写易漂移实现。

后续新增少量本地检查/预览聚合命令时，应复用现有底层命令，报告它们实际完成的范围；构建会更新身份，启动会使用 profile，不伪装成只读检查。最终名称与接线由实施者确定，不逐命令询问。

## 扩展后的闭环怎样验

针对一次查询接口修改，应能做到：任务读取相关模块与问题 → 经验导出消费者检查 → 聚焦测试和必要构建 → 适用的正式 Browser/Desktop 操作 → 保存候选与预览证据 → 失败写问题、复验写证据、原因形成经验。

这个例子强调材料被消费、命令被执行、结果能追溯；仅新增几份同名文件不算完成。预览工具接线与实际产品/模型修复分别交付，不把一项通过覆盖其他缺口。

## 经验的前后端分组建议

用户已采纳分组但保持统一索引的方案，按实际职责而非简单语言/目录分类。当前入口与分组记录见根LESSONS和CONTRIBUTING，实际消费证据见本轮检查点。

- **共通工程经验**：候选身份、范围、验证有效性、失败记录、文档归属与 WIP。
- **界面与交互经验**：共享 Renderer、原生窗口交互、焦点、布局、主题、草稿呈现、用户反馈与 DESIGN 对照。
- **Host 与执行经验**：Library 权威、事务、权限、Worker、资源、取消、未知提交与恢复。
- **跨端/端到端经验**：Client/Host 契约、迟到响应、切库撤权、保存回读、任务结果与 UI 同步、文件交接。

一条事件只保留一个主记录和证据入口，可带多个适用模块标签、分别列各层必须检查的动作。不要前端抄一遍、后端抄一遍后分别修改。

例如“切库后旧 AI 结果仍显示”：Host检查结果资格与当前库代次，Client检查上下文，界面拒绝旧响应与保留当前输入；需同一条跨端经验覆盖这些动作。只修界面隐藏或只增加 Host 拒绝测试，都不能替代正式用户路径验证。

开始只保留少量有证据的条目；当某类足够多时才拆详细文件。任务加载共通要求和命中的职责/模块经验，不强制所有前后端任务读全量案例。

## 子系统文档究竟描述什么

docs/subsystems/README.md 在 Magpie 中是子系统参考的目录与维护/审查说明，不是把软件所有功能、技术栈和历史全文放在同一文件。每个子系统可以跨多个源码包甚至仓库。

DAM 的整体技术栈、进程拓扑、状态权威和依赖方向由 ARCHITECTURE.md 解释；子系统索引指向相关文档；模块文档解释具体机制，交互规格解释用户行为。具体依赖版本以 package.json、锁文件与实际运行资格为准，不在所有模块重复抄版本号。

模块说明应覆盖：

1. 负责的用户能力与边界，明确哪些事情不由它负责。
2. 输入、输出、接口和实际调用者，链接关键源码/符号。
3. 谁拥有数据与状态，保存与事件如何到达消费者。
4. 主要执行路径、状态转换与重要不变量。
5. 失败、取消、并发、恢复、兼容和权限语义。
