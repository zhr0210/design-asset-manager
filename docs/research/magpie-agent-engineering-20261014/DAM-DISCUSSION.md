# DAM 开发反馈闭环：访谈与已确认方向

更新：2026-10-15，Asia/Shanghai。

这是本次研究衍生的讨论记录，不是实施任务、产品当前状态或已生效的开发规范。待确认方案不写入 AGENTS、TASK、DESIGN 或架构决定。明确的新领域术语归 CONTEXT；难以逆转且有真实取舍的决定才进入 ADR。

## 已确认的用户方向

用户采纳前轮改进建议，特别强调：让 AI 知道读哪些文件、写到哪些文件，并让规范、失败记录与问题影响下一次工作。

- 项目目前未公开开源，不依赖公开 GitHub 社区作为反馈前提。
- 优先按前轮推荐建立稳定性闭环：从已有回归缺口和核心用户路径入手。
- 反馈来源可以是用户实际使用、正式应用回归、已有诊断和返工记录。
- 复用现有项目文档分工，避免增加与权威文档冲突的规范。
- 用户采纳任务触发方式：每次明确开发任务启动时自动消费相关问题与经验，在任务范围内完成修复、验证和写回；目标完成后停止。本阶段不增加定期无人值守巡检。
- 用户选择仓库内本地记录作为开发问题的权威载体，不以私有 GitHub Issues 作为本闭环的前提。
- 真实验收允许真实 AI Worker 和外部推理，仅采用现有模型，不允许模型下载。
- 每次修改涉及 UI/UX 时，必须依据根 DESIGN.md 及其指向的相关交互规格，检查受影响范围。缺陷修复若无法复现报告场景并验证问题根源及修复效果，不能标记问题通过。
- 用户采纳统一经验入口、按共通/界面交互/Host执行/跨端职责分组的方案；同一事故保持一个主记录，可关联多个模块。
- 用户采纳子系统索引、整体架构与模块说明分层，以及复用现有 CI/npm 入口和按目标平台验证的适配方式。
- 2026-10-15先采纳上述方案并延期；随后明确“采纳并开始”。本地反馈接线已完成，实际结果与限制见[本轮检查点](../../checkpoints/development-feedback-20261015/README.md)。原延期是历史决定，不作为当前实施禁令。

以上确认不等于无人值守巡检、恢复全部历史任务、扩大资料/账号范围或自动发布的许可。

## 拟议的读写消费流程

以下保留访谈收敛的流程说明；本阶段实际接线与验证以检查点为准。

1. 开始一个明确用户任务时，先确定结果、范围与完成条件。
2. 按现有路由找到权威规格、实际调用链、测试，以及与本任务有关的问题和经验。
3. 用当前代码/版本判断记录是否仍适用；用户最新要求覆盖旧下一动作。
4. 把适用经验转换成具体检查，不仅声明已读过。
5. 执行后记录行为、版本、验证与未执行项，保留原失败证据。
6. 一次问题形成可复现的开发问题；重复返工再提炼可执行经验。产品决定变化仍按相应权威归属记录。
7. 下一任务按相关性找到经验并执行检查；稳定的机械要求可进一步放到测试或工具里。

## 拟议写入职责

| 内容 | 归属或待决定事项 |
| --- | --- |
| 当前任务实施范围 | 获准实施后更新 TASK；跨系列状态依现有主台账 |
| 实际运行能力、候选及资格缺口 | CURRENT-STATE，链接详细证据 |
| 一次失败的复现、原因和复验 | 对应任务/模块的证据记录；开发问题索引载体待决定 |
| 可复用经验 | 经验载体、模块归属、去重与读取方式待决定；不先创建全局 LESSONS |
| 稳定高频工程要求 | AGENTS/CONTRIBUTING 或相关模块规范；机械检查放适用测试/工具 |
| 已确认视觉规范 | DESIGN；失败日志和访谈过程不写进去 |
| 用户流程、状态与保存取消语义 | 对应模块交互规格 |
| 技术机制 | 架构或模块 README；重大不可逆取舍才作 ADR |

## 已收敛：闭环的启动方式

**闭环的启动方式：**

- 方案 A：每次明确开发任务启动时，自动消费相关问题与经验；任务内连续完成修复和验证，到目标结束停止。
- 方案 B：在方案 A 之外，增加定期无人值守巡检，发现问题后按预先确定范围推进。

2026-10-15用户采纳方案 A。先验证记录确实能进入下一次检查；方案 B 留待以后明确决定，本阶段不创建定时自动化。

## 已收敛：开发问题的权威记录载体

- 方案 A：仓库内本地开发问题记录。现有任务主台账链接相应问题明细；明细保存复现、认领、原因与复验，原始证据仍留在对应检查点。TASK保存当前获准任务，CURRENT-STATE保存实际能力，不重复建立第二份跨系列进度台账。
- 方案 B：私有 GitHub Issues 作为开发问题权威记录，仓库保留规格、经验和验证证据链接。不要求公开开源或公开社区反馈，但后续读写依赖远端工具和授权。

2026-10-15用户选择方案 A。使当前闭源阶段的用户反馈、回归失败和诊断问题可被本地任务直接消费。GitHub 仍可用于已有明确引用的任务；不要求上传本地问题或公开资料。
