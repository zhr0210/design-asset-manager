## 二、每份文件实际怎样写

### 1. CLAUDE与AGENTS：装载与阅读触发

[CLAUDE.md](sources/magpie/CLAUDE.md)只有两项引用：AGENTS和LESSONS。这说明在Claude Code侧，作者还显式装载整份经验；不能把我们的按模块筛选经验说成作者的同款实现。

[AGENTS.md](sources/magpie/AGENTS.md)前四节是：改已有子系统前读设计参考并核对源码；写/审代码对照开发规范；审社区PR前读贡献治理；改代码前读经验。它不是只贴文件目录，触发动作和阅读目的写得明确。

后半部用订阅移交说明“哪份代码真的执行”。已经移交给插件的用户，登录、请求、用量和错误都由插件负责；修内置旧代码不会到达这些用户。它给出判断线索、源码名、修复顺序和parity测试位置。入口承载的是会影响选错实现的关键上下文，不追求纯链接形式。

**对DAM的启示：** 四类短约定与任务导航可以保留。Mac原生B窗/旧Electron工作窗、Browser/Host或实际Runtime归属不能被一张共享React技术栈表抹平；相关任务应尽早定位正确执行路径。是否把少量高频分支线索放在根入口，按误判风险决定。

### 2. code-standards：规则旁边写审查怎样判断

[开发规范](sources/magpie/docs/code-standards.md)第一句话就说明规则来自反复的PR审查要求，审查者逐条核对，不满足时指出具体条款。主体结构是：

- 变更包含什么：目标范围、准确分类、全路径、同类入口、依赖假设、未知读取、第三方真实格式、并发与边界。
- 测试：修复前真实失败、破坏保证后失败、真实形状fixture、行为断言、隔离、不受控网络、收尾与时序。
- 六项验收：回退验证、隔离、构建/套件、GUI引擎/语言、真实使用、GUI规则。
- 合并与发布：当前main合并候选、被审head、记录实际检查、CI完成、产物齐全与Latest。
- 审查步骤、Go局部规范、GUI决定、提交正文。

最重要的写法是“要求＋审查对象＋具体失败证据”。例如改变公式或断点，应检查所有基于旧含义的调用者与测试；测试声称保护一个保证，审查者就故意破坏它，看测试是否真正报错。这比“代码要优雅”“测试充分”更能指导行动。

其语言/GUI规则也很具体：翻译、应用自己的菜单、不因点击擅自滚动、不用彩色左边条。它们属于这个产品的已确认选择，不是所有项目的通用审美。

**对DAM的启示：** 独立开发规范值得建立，但从现有保证提炼，用“适用条件/要求/检查依据”表达，不把工程指南、DESIGN和模块说明再复制一遍。Go命令、固定全套政策和菜单偏好不照搬；适用平台、原生与Browser分别验证。

### 3. docs/subsystems：当前机制的参考与变更审查协议

[索引](sources/magpie/docs/subsystems/README.md)除了11项能力导航，还包含三段维护规则：

1. 改责任、接口、状态转换、运行路径、兼容或失败行为，同一PR更新所属参考；内部重构保持契约时不强制改文。
2. 每项语义事实保存一处，链接源码文件和符号，不机械复制易变实现。
3. 变更说明交代触发条件与前后行为；审查沿调用者和状态追到实际执行，再核对文档与验证覆盖。

很多专题采用相近结构：能力/范围→职责与权威来源表→运行链→约束/失败/兼容→Verification。并非完全统一模板：Claude桥按会话/进程生命周期展开，插件运行时按逐步落地的能力边界展开。

例：[同步备份](sources/magpie/docs/subsystems/sync-backup.md)直接说明谁保存配置、版本与撤销文件，远端条件写使用什么版本标识，两个电脑并发怎样合并，读失败为什么必须是未知，CLI/GUI怎样调用相同操作，以及相应测试。它不是只有技术名词和目录清单。

例：[插件运行时](sources/magpie/docs/subsystems/plugin-runtime.md)不仅描述模块，还链接架构保护测试。实际[TestPluginsImportOnlyCore](sources/magpie/internal/pluginrt/pluginrt_test.go)检查核心不导入插件、插件不互相导入、统一入口收集所有插件。机制被源码检查消费，而非只存在文档。

文档并不短：部分专题几十KB到约180KB，且有很长的行。作者把深入上下文放在相关能力处，不能据此说下游也都必须精简到几百字。DAM应控制可发现性与适用范围；篇幅大时按章节导航，但不以字数掩盖不清晰职责。

### 4. LESSONS：规则、原因、证据、复盘日期与正例

[LESSONS](sources/magpie/LESSONS.md)从首轮快照约504行增长到本次616行。按读题、修一类问题、用户文件、验证、并发、红测试、合并/关闭等归类，包含失败与Done right。它还记录规则已迁入规范之后又被漏掉的事实，不把提升视为一次性解决。

作者对Seen的原始定义是复盘发现问题的日期数；跨至少三个日期后迁入开发规范。原文没有写我们提出的“必须三起独立新事故”的完整计数算法，因此这层去重和证据结构要标为DAM适配，不能归因作者已经如此实现。

“严重安全问题不等第三次”的处理方向与其风险先查、当日修补案例一致；本轮未找到作者把它写成一个通用的Seen例外字段或自动机制。DAM已明确的立即处理保护依用户决定落实，不依赖外部仓库再授权。

新例子：PR #1354的页面布局技术上通过审查并发布，用户同日要求恢复，随后整体回退。LESSONS将问题归为合并决策，并要求社区布局提案有明确需求来源。它没有把返工简单归罪作者，也没有等待Seen 3×才处理当次问题。

**对DAM的启示：** 不需要先建设复杂经验平台。日期、事件证据、适用模块和候选去向应足够清楚；同一条经验升级后保留链接，下一次相关任务实际做检查。工具提示候选与Agent评估规则是两层，不自动向AGENTS加禁令。

### 5. contributors：公开贡献的风险与成本治理

[contributors](sources/magpie/docs/contributors.md)分为先查危害、无需完整审查的关闭条件、封禁提议和具体观察名单。新增workflow/发布脚本、外发目的地、无关凭据访问、依赖或可执行内容等，先定位具体风险行，再由维护者判断。

特别明确的是Agent只提封禁建议，维护者决定。观察记录同时补充贡献者后来做对的案例，避免把观察名单误读为永久否定。

**对DAM的启示：** 当前无公开贡献者，不需要照搬名单与拒绝流程。目标一致性、完整diff、执行边界和验证声明的核对仍有用。所有者委托自己的AI修改必要依赖，与不可信外部PR不是同一种审批场景。

## 四、UI preview如何工作，以及为什么不是验收

[预览README](sources/magpie/.github/ui-preview/README.md)和脚本显示：根据PR差异识别UI影响→构建nogui版本→Linux隔离目录启动真实web/gateway→填充模拟providers、请求、会话和配额→发送少量真实DeepSeek请求→让模型根据diff、代码和可见页面轮廓规划场景→Chromium操作→截图及适用mp4→将结果放入与PR/SHA关联的预览区域。

值得借鉴：

- 以具体变更规划场景，通常只看少量相关页面，不跑无关演示。
- 图注描述做了什么/看什么，而不替审查者宣布结果正确。
- 环境看不到的状态写unseen；步骤失败记录errors；PR描述与代码不符单独提示。
- 有交互或跨页变化才保留视频；截图永远生成。材料保留候选身份。
- 执行候选代码的job与有仓库写权限的发布job分离。

但它的范围也明确：Linux脚本只在Linux隔离，使用大量mock；单页可通过view参数直接打开；失败后允许模型修补余下计划；有部分有效画面时仍可发布错误说明。这些能力有助审查，不是原生平台验证、原问题复现或根因修复证明。

workflow还明确承认候选代码可以读取低额度模型key。这是作者选择的风险范围，不移植到DAM。DAM继续由应用安全机制内部使用账号，不让Agent读取秘密；也不为学习预览脚本而生成CA、代理真实认证或上传截图。

**DAM要求更明确：** 每次影响UI/UX均按DESIGN与交互规格检查适用正式入口；原问题未复现、根因未核对、效果未证明就不关闭问题。可以借鉴场景/画面/身份材料，但不以规划器的成功状态或自动改路绕过原失败。

## 五、两项实际审查与一项最新修复

### PR #1328：审查者补构造真实时序，抓到新性能问题

[第一次审查](https://github.com/yetone/magpie/pull/1328#issuecomment-6063617478)报告新测试和race通过，但审查者用append→立即读→稳定后再读的时序发现历史全量重建，分配量从135增加到32434；已有性能测试因改成预先稳定的时钟，反而绕开了问题。

[第二次审查](https://github.com/yetone/magpie/pull/1328#issuecomment-6066773023)再核对新head合并当前main后的结果，记录Windows真实NTFS ChangeTime检查和六种break checks，并将仍存在的成本另行登记。这是“自己构造能区分假设的反例”，不是只读实现者报告。

### PR #1354：技术通过不代表布局值得改变

[合并前记录](https://github.com/yetone/magpie/pull/1354#issuecomment-6163212821)报告82个GUI文件、两引擎大部分通过、47项旧代码回退失败，还列出已登记红项及未试WebKitGTK/WebView2/真实gateway。

[回退说明](https://github.com/yetone/magpie/pull/1354#issuecomment-6165936194)表示用户认为新布局更难读，整体撤回。后续经验要求布局变更有明确需求来源。这证明“新增测试验证新设计符合自身预期”不足以回答“应不应该换设计”。

### 最新代理端口修复：从超时现象追到根因，再写回经验

[9a852ae9d](https://github.com/yetone/magpie/commit/9a852ae9dbb22bf93b19449323e4315e2f974cba)正文解释：已释放的死代理端口被桥重新分配，桥向自身发送请求，形成一分钟等待；此前被当负载抖动。记录称注入端口复用时旧代码60秒失败，修复后包2.4秒完成，反向破坏新保证时测试失败，并明确未测Windows。

紧随的[95e7c6bcc](https://github.com/yetone/magpie/commit/95e7c6bcc07629897f6703c31eaef477fcee4a13)将已找到的原因写回LESSONS。它是本次最直接的“现象→复现/原因→修复/测试→经验更新”可追溯样例；执行时间是公开记录，本轮未重跑。

## 六、对DAM方案的调整建议

以下是研究建议，不自动改写已生效规范，也不把尚未被用户采纳的独立开发规范标为现行文件。

1. **AGENTS保留短约定和动作触发。** 写代码/审查前读开发规范，改模块前读实际路径，UI改动前读DESIGN/规格，任务结束写回问题和经验。不要只贴文件名，也不再把所有细则填满根指南。
2. **独立code-standards承接可审查保证。** “规则＋审查怎样判断＋依据/反例”，通用要求和平台/能力条件分开。允许AI自主选择实现，结果要能被检验。
3. **保留已有文档权威，减少额外仪式。** DAM已经有CONTRIBUTING、DESIGN和真实验收流程，可保留；开发规范链接它们，而非各自全文复制验收条款。无需再创建一套重复subsystems地图或空模块文件。
4. **模块文档应增加语义变更消费规则。** 变更说明从触发和前后行为出发，审查核对实际路径、相邻消费者、文档和证据；纯内部重构不要求写一篇新报告。
5. **LESSONS先有真实案例，再升级合适保证。** 沿用用户确认的三日期候选与严重风险立即处理；去重/提示工具属于DAM设计，按需要实现与验证，不假装作者已有同一工具。
6. **预览负责展示，验收负责判断。** 为每项受影响任务留下当前候选的画面/步骤/错误，正式用户路径与原生专项单独成立；本地保存，不默认上传。
7. **审查敢挑战新增测试。** 看真实顺序、边界、相反方向、故障和性能，既不只相信实现者全绿，也不为每个可逆小改要求全套破坏实验。
8. **稳定保证逐步有执行消费者。** 保护测试、候选校验或CI配置能检查的不要永远只依赖聊天记忆；无法机械判断的产品取舍保留明确责任与证据。

这次重读支持独立开发规范，但也提醒我们：真正要学的是工作中会消费的文档与证据，不能把目标变成建设更多规范文件和自动化平台。
