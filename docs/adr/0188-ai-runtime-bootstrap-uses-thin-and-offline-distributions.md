# AI Runtime Bootstrap Uses Thin And Offline Distributions

The target distribution design provides two platform/architecture-specific distribution forms backed by one runtime package protocol. The default **Thin Installer** contains the desktop application, trusted Bootstrap control plane, signed catalog roots, versioned baseline manifest, downloader, verifier, transactional installer/rollback logic and AI Worker source/control metadata, but not model weights or the complete executable AI environment. The optional **Offline Full Installer** contains the same application and exact verified baseline runtime packages as bundled payloads. It is not a separate product, runtime layout or dependency graph.

The first application launch starts with **Library Start**, where the user creates, adopts, opens, or restores one portable library. Once that library is usable, Asset Workspace opens without waiting for any AI runtime. **AI Environment Setup** is then offered as a resumable non-blocking first-session step before ordinary local-AI use; leaving it does not make import, preview, organization, lexical search, or Original Handoff unavailable. Bootstrap detects only platform/runtime evidence needed for compatibility, shows the selected baseline package identities, source mode, exact/estimated download and installed bytes, destination class, trust/license status, network-cost state and fallback limitations, then initializes a managed self-contained AI environment. Under ADR 0483, the trusted setup review requires an explicit user choice before downloading or installing the disclosed baseline, on every network class and for bundled payload installation. One accepted setup plan may cover the disclosed baseline plus selected model/dependency assignments under ADR 0170, with Pause and Skip available while ordinary Asset Workspace use continues. Unmetered evidence alone is not consent. Offline, Metered, Roaming and Unknown retain ADR 0177 admission/exception rules within that grant; new source, license, permission or storage scope requires review rather than hidden traffic. Failure or Skip leaves the non-AI asset manager usable and the setup surface resumable.

The Baseline AI Runtime includes a pinned app-managed Python/runtime executable where required, the AI Worker execution environment, common decoding/preprocessing bridges and the smallest platform-compatible dependency closure needed to host supported local capabilities. It installs under governed Managed Paths and never modifies system Python, global package stores, shell profiles, PATH, operating-system frameworks or another application environment. The application does not probe a user Python installation as the production dependency once its managed runtime is ready. Package identity, digest, signature/trust, platform/architecture, extraction bounds and executable readiness are verified before atomic promotion and Runtime Registry commit.

The baseline does not install every accelerator backend, model family adapter or optional capability pack. Model weights are never downloaded by post-library Bootstrap. Selecting a model in Model Library remains explicit under ADRs 0152 and 0170; that reviewed model transaction automatically expands and installs its exact required runtime/capability dependency closure without separate repetitive confirmations. New license, gated account, sensitive permission, non-default storage or ADR 0177 network exception still requires its own review. GPU drivers, kernel/system extensions, vendor control software and system-wide CUDA/ROCm components are detected but never automatically installed or elevated by the application; an eligible managed CPU or platform-native fallback is offered instead.

Offline Full Installer runtime payloads use the same immutable manifests, digests, trust evidence, extraction rules and managed destination as remote packages. Bootstrap copies and verifies them from signed application resources into the managed runtime root rather than executing mutable state inside the signed app bundle. After installation, Runtime Registry records the same package identities regardless of bundled or remote source, so Doctor, repair, model dependency resolution and later compatibility checks do not branch by distribution form. Missing or damaged bundled payloads fail closed and never fall back to an unverified system environment.

ADR 0206 requires Thin Installer online payloads to pass Fresh Trust Install Admission and requires Offline Full Installer payloads to carry signed Dated Offline Trust Evidence. Offline Bootstrap shows the evidence issue date/freshness, rejects any package covered by newer known revocation state and never claims a latest-online check. Passing the offline trust gate preserves this ADR's network-independent baseline installation; it does not add model weights or bypass the displayed Bootstrap decision.

ADR 0207 forbids an application-invented age-only expiration for that offline evidence. A long-stored Offline Full Installer remains eligible when exact signatures, any signed validity window, compatibility and known revocation checks pass; the UI still exposes its evidence age. A newer installer's existence or an expired signing credential after a trustworthy in-validity signing time does not invalidate it by implication.

If an Offline Full Installer exceptionally carries a signed current-time installation boundary, ADR 0208 requires trustworthy current-time evidence and blocks as Time Not Assessable when the host cannot establish it. Baseline packages without that boundary preserve normal air-gapped Bootstrap and do not require network/time synchronization solely because of age.

ADR 0212 makes no-boundary behavior mandatory for the Official Stable Offline Full Installer. Only an explicitly classified test/preview, legal/license-window or security-incident transition artifact may carry a signed boundary and complete time-bound justification; it cannot be presented as the stable offline distribution.

The Thin Installer minimizes ordinary application/update transfer and lets platform-specific runtime payloads be serviced independently. The Offline Full Installer prioritizes predictable deployment without network access at the cost of a larger artifact. Release Flow publishes and verifies them as separate artifacts for each supported platform/architecture and makes their included runtime versions and sizes visible; the offline artifact must not silently become less complete than its declared baseline. ADR 0189 owns GitHub-primary signed runtime discovery, mirrors and offline source equivalence. ADR 0190 owns side-by-side unattended security/compatibility patches and reviewed major runtime changes. Application updates do not delete a working runtime merely because a newer baseline exists.

ADR 0002 continues to govern external inference, model selection, service start and ordinary managed-runtime additions. ADR 0483 replaces the former automatic-install exception; this ADR supplies distribution and verification mechanics within an explicit reviewed setup. ADR 0170 continues to require explicit review before model artifacts and capability assignments; its runtime dependency rows may show Already Installed after Bootstrap. Restoring ADR 0185 dependency inventory never auto-downloads models, but missing dependencies selected through a later model/extension recovery plan use the same package machinery.

The current package copies `ai-service` sources through Electron `extraResources` while excluding `.venv` and model weights, and production resolution can still fall back to host Python. Bootstrap, Runtime Package planning/execution and Runtime Registry structures exist, but the default manager uses a sample metadata manifest and manual confirmation flow; there is no production signed remote baseline catalog, self-contained cross-platform AI runtime payload, post-library AI Environment Setup product page or offline-full artifact assembly. This ADR changes documentation only: it downloads nothing, launches no runtime, reads no model/cache/user asset/runtime database, and changes no public IPC, schema or AI Worker API.
