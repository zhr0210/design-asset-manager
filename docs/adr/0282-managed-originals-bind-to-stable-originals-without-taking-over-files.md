# Managed Originals Bind To Stable Originals Without Taking Over Files

Each library has exactly one **Managed Originals Directory Binding** in its Library Manifest. A newly created binding defaults to the stable cross-platform root-relative name `Originals`; the product may display the localized role label “原始素材” without renaming the filesystem directory when language, device, or platform changes, and an alternate binding shows its actual disk name alongside that role. A user-selected alternate remains a non-hidden safe relative proper descendant of the same Library Root and must be valid on both supported desktop platforms; `.`, absolute, home-relative, URI, traversal/escape, linked, junction/reparse, mount-escape, special-file, Library Control Directory, cache, runtime, model, plugin, and nested-library targets are rejected. Lexical containment alone is insufficient: inspection proves the resolved physical boundary and required regular-file, atomic-update, and lock semantics.

Library creation, In-Place Reference Library adoption, restore, and Material Library Migration inspect the proposed location before any binding or file write. An absent location may be created after confirmation, and an empty ordinary directory may be bound only as part of that reviewed operation. Empty means no entry of any kind, including hidden or operating-system metadata, after target-filesystem case folding and Unicode normalization have resolved equivalent names such as `Originals` and `originals`. A location already bound by the same valid Library Manifest may be non-empty and is reused only after manifest, physical-boundary, authoritative inventory, and owned-file inspection succeeds. Any non-empty unbound directory, differently bound directory, or location whose ownership cannot be proven is a blocking collision: the application does not overwrite, merge, rename, delete, enumerate as assets, adopt, import, or infer ownership from its contents.

On collision, the user must explicitly create or select another empty safe directory inside the Library Root. The application may suggest a collision-free name but never chooses a suffix or takes over a folder silently. Binding runs under the library's exclusive setup transaction, rechecks physical containment and emptiness immediately before its journaled manifest commit, and on failure removes only a directory created by that transaction that is still empty; a concurrent unknown entry stops the operation and is never cleaned. The accepted relative path becomes the permanent physical-boundary exclusion used by Reference Adoption Scan, Progressive Reference Indexing, reference monitoring, Source Tree, and Folder Collection Mapping; aliases cannot bypass it, and unknown files are not turned into Candidate Artifacts, Managed Assets, or Referenced Assets merely because they occupy or later appear at that path.

A colliding unbound directory that was not selected remains outside the Managed Originals Directory Binding. In an In-Place Reference Library, it may appear only as an ordinary proposed source scope in the later read-only Reference Adoption Scan Plan; explicit adoption confirmation, exclusions, and normal validation decide whether its eligible files become Referenced Assets. The binding flow itself neither imports that content nor permanently hides it from the reviewed source plan merely because the folder is named `Originals`.

Changing an established binding is an ADR 0276 Material Library Migration governed by ADR 0003. Its dry run verifies every owned file, destination emptiness/collisions, cross-platform path legality, required space, active pins and rollback, then moves or copy-verifies item-atomically only after explicit confirmation and atomically switches database paths plus the relative manifest binding after complete validation. Old-directory cleanup remains a separately reviewed consequence and never removes unknown entries. A missing or externally renamed bound directory never causes the app to create a new empty `Originals`, fall back to application data, or bind another same-named folder; Library Open Inspection keeps managed writes unavailable and routes to evidence-based locate, restore, or migration recovery.

ADR 0283 governs changes to known owned files beneath a still-valid binding. Its item-scoped reconciliation cannot repair, replace, rename, or infer the Managed Originals Directory Binding itself and cannot use a file-level recovery outcome to bypass this ADR's collision or boundary inspection.

Full Library Backup includes the binding role and logical relative location in the portable manifest while continuing to identify every original by library identity and digest rather than by display label or absolute path. Restore into a new Library Root applies the same empty-destination preflight and cannot overwrite an existing `Originals` directory. ADR 0283 governs external entry changes, ADR 0284 governs item recovery, ADR 0285 governs shallow storage buckets plus stable readable names, ADR 0286 fixes the v1 sequential 2,000-commit bucket allocation policy, ADR 0287 fixes the short disambiguator, ADR 0288 fixes the Unicode-preserving readable stem, ADR 0289 fixes the real-format-derived extension, ADR 0290 governs insufficient path headroom, and ADR 0291 fixes its portable and platform budgets.

The current implementation has one settings-level library path and a normalization service that writes to an unbound singular `original` subdirectory using source basenames. It has no per-library manifest binding, safe empty-directory claim, cross-platform collision plan, or managed-originals migration. This ADR records target architecture only and creates, binds, scans, imports, migrates, reads, moves, or deletes no runtime directory, user asset, database, cache, model, or plugin data and changes no public IPC, schema, or AI Worker API.
