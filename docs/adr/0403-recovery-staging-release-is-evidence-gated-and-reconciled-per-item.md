# Recovery Staging Release Is Evidence-Gated And Reconciled Per Item

Interrupted-operation staging may consume significant space, but generic cleanup cannot know whether those bytes still prove an outcome or protect user data. Recovery staging is therefore releasable only through explicit evidence-gated operation recovery, never through cache policy, storage pressure, or remembered cleanup consent.

Storage Management offers **Release Safely Rebuildable Recovery Staging** only after a fresh read-only check proves that the exact bytes are solely owned by the interrupted unit, remain unpublished, crossed no replacement or destructive boundary, are unnecessary to determine the outcome, and can be rebuilt from governed inputs. Review shows safely calculable bytes and the full-reprocessing consequence. Success removes only proven operation-owned staging, retains the minimal journal/receipt, and records **Safely Paused Without Staging**. Ambiguous, shared, irreplaceable, or outcome-bearing staging is ineligible.

A **Recovery Staging Release Batch** begins with no selection and permits explicit selection of eligible items or Select All Currently Eligible. One review and confirmation covers only that selection. Each item repeats complete proof immediately before mutation and commits independently; evidence drift excludes or fails only that item, while already proven releases remain valid. There is no batch rollback, future rule, remembered selection, or pressure-triggered equivalent.

An in-flight batch supports **Cancel Remaining Recovery Staging Releases**, not pause/resume. Cancellation durably prevents dispatch of the next item; the current item settles truthfully, and undispatched items become Cancelled Before Release with unchanged recovery state. Quit, crash, or restart never resumes undispatched work. A later release requires a new current-evidence plan and confirmation.

Before changing a multi-member staging set, the operation journals opaque expected-member identities and release intent, then records each member outcome. After interruption, reconciliation is read-only: all members proven absent means Released; all proven present and unchanged means Release Failed with staging retained; any mixed, changed, or unassessable set means **Staging Release Reconciliation Required**. No path, filename, payload, or raw operating-system error enters aggregate UI or lightweight history.

The reconciliation view may list, filter, and sort items but has no multi-select or batch recovery action. **Complete Remaining Recovery Staging Release** is one separately reviewed item action available only after fresh proof that every remaining member is solely operation-owned, unpublished, outside destructive boundaries, and unnecessary for outcome determination. Confirmation repeats that proof. Drift causes no mutation and consumes the confirmation. Success records **Released After Reconciliation**, merges into the original batch item, and leaves the owning work Safely Paused Without Staging; it never restores absent members or resumes interrupted work.

Every confirmed completion is a path-free **Recovery Staging Completion Attempt** in the same recovery item. State-changing attempts remain distinct; only consecutive no-change attempts with identical evidence generation, membership counts, outcome, proven bytes, and typed reason may compact into occurrence count with first/latest time. Manual attempts require fresh proof and confirmation, have a visible count but no arbitrary limit, and never enter ADR 0092 automatic retry limits.

The batch result classifies items as Released, Proven Already Absent, Cancelled Before Release, Staging Release Reconciliation Required, Excluded After Evidence Change, or Release Failed, and reports Complete, Partial, None Released, or Cancelled. Only post-operation evidence-proven physical reclamation contributes reclaimed bytes. **Retry Failed Staging Releases** creates a new explicit current-evidence plan for Release Failed items only; it never includes cancelled, ambiguous, excluded, or reconciliation-required items automatically.

Each batch creates one ADR 0086 Reviewed Batch Action retained for 30 days by default under ADR 0087. History attention is separate from operational recovery attention and authority. ADR 0400 permits at most one aggregate terminal notification for a user-confirmed long-running batch under its foreground, permission, and preference gates; cancelled batches and read-only reconciliation remain silent. ADR 0401 governs lifecycle-bound terminal markers, explicit unknown-outcome retirement, and anti-replay evidence after activity history expires without reviving the interrupted operation or broadening release authority.
