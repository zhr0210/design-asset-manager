# Optional Companion Removal Separates Detachment From File Disposition

**Remove Optional Companion** is available only for one capability-declared optional role after the current source evidence and complete remaining member set validate. The review names the preview, analysis, metadata and Original Handoff consequences and never permits removing a primary or required member. Success retains the Design Asset and Compound Original Identity even when only the primary remains, commits one new Source Content Generation and stales prior-generation derived evidence; it never rewrites any retained member or creates an independent asset from the former companion.

For a Referenced Compound Original, removal atomically deletes only the Referenced Compound Member Relationship and leaves the user-owned source file unchanged at its current path. The application stops applying that member to its own preview, analysis and Original Handoff after commit, but the review warns that an external application opening the primary may still discover and apply the adjacent file. Physically moving, renaming or deleting that now-untracked file is outside the completed relationship-removal action and is never implied by it.

For a Managed Original whose optional member is still present, confirmation requires one explicit disposition. **Keep Detached Copy** is the default: the application copies the exact member to a user-selected safe external destination, refuses overwrite or silent unique naming, and byte-verifies the copy before any managed byte changes. **Move Detached Companion to System Trash** skips the external copy but requires a distinct destructive choice. In both cases the application journals the current generation and full group, blocks source-dependent use at the first managed-member trash request, requests operating-system trash only for the exact optional member, then validates the remaining group and atomically commits the reduced manifest and new generation. The existing Compound Original Directory and identity remain valid rather than collapsing back to single-file storage.

Cancellation is complete only before that trash request. Afterward, failure, interruption, ambiguous trash evidence or unproven manifest commit enters **Optional Companion Removal Recovery**; the application never repeats an ambiguous destructive request or claims rollback. Freshly validated recovery may finish the reduced manifest when the member is proven absent and the remaining group is valid, or restore the exact prior member through its receipt when its declared path is safely vacant, then revalidate the prior group. A verified Keep Detached Copy remains a separate user-owned file in either outcome and is never deleted during recovery.

If an optional companion is proven physically absent, removal is a non-destructive manifest repair after the application validates the remaining group; it makes no trash request and never deletes a later file merely because it appears at the remembered path. A present, unreadable, invalid or physically ambiguous managed member never receives that absent-member shortcut: it must complete the applicable ownership-specific disposition safely or remain degraded/recovering. Referenced and managed success both preserve all retained members and user-authored organization. The current application has no ownership-specific optional-companion removal review, detached-copy flow or group removal recovery. This ADR records target architecture only and reads, copies, validates, moves, restores, trashes, groups or deletes no runtime/user file, directory, database, cache or system-trash item and changes no public IPC, database schema or AI Worker API.
