# Notification Permission Is Requested Contextually Once

Design Asset Manager does not request operating-system notification permission during first application launch, ADR 0188 AI Environment Setup, library creation/open/restore/merge, automatic catalog refresh or ordinary AI onboarding. Initial permission state is **Notification Permission Not Requested** while ADRs 0175/0201/0400 class preferences retain their desired default-On values. No automatic trust event, background job or incoming advisory may surface an unexpected permission prompt.

The application may offer one contextual **Notification Permission Primer** only after either: the user explicitly chooses Enable System Notifications/turns on a class in App Settings, or the user confirms a Long-Running Application Operation whose completion may occur after leaving its surface. The primer explains the eligible notification classes, aggregate/content-free projection, absence of per-item/progress notifications, device-local switches and OS control. It offers **Continue To System Request** and **Not Now**; it is non-blocking and the operation/setup proceeds normally either way.

Only Continue To System Request calls the platform adapter's actual permission request when the OS supports one. Not Now keeps permission Not Requested and does not schedule another primer. A later explicit Enable System Notifications action may reopen the primer, but startup, subsequent operations, trust refreshes and elapsed time cannot. If the platform grants permission, enabled classes become deliverable prospectively; no suppressed/past transition is replayed.

If permission is denied, restricted or later disabled in system settings, the application records a safe **Notification Permission Unavailable** reason and never loops the OS request or primer. App Settings shows one passive status and a user-initiated **Open System Notification Settings** action when the platform supports a trusted destination. The app does not open settings automatically, deep-link from background work, claim it can change OS policy or repeatedly prompt the user to reverse the choice.

Notification permission state and ADR 0201/0400 class preferences remain separate. A class may be preferred On while OS delivery is Not Requested/Unavailable; in-app attention remains complete. OS permission does not enable every class the user disabled, authorize AI or other background execution, grant network access or change result/library state. Revocation/containment applies even with no notification permission.

Platform adapters map macOS and Windows capabilities into one shared status vocabulary: Not Requested, Allowed, Denied/Unavailable and Not Supported/Not Assessable with source/freshness. Where an OS version has no application-triggered prompt, Continue leads only to truthful platform guidance/settings and never fabricates an Allowed result. OS Focus/Do Not Disturb/lock-screen delivery are not permission states and are not bypassed or continuously probed.

Permission/primer state is device-local App Settings metadata excluded from Full Library Backup. Logs/public state contain only enum, timestamps for the user-triggered request/result and safe reason category—never OS account/device identity, private settings paths or notification content. Permission denial is not an error notification or AI health failure.

The current project has no shared permission vocabulary/platform adapter, contextual primer, user-triggered system-settings action or separation of desired class preference from deliverability. This ADR changes documentation only: it requests no OS permission, opens no system settings, sends no notification, reads no device/private state and changes no public IPC/schema/AI Worker API.
