# Runtime Security And Compatibility Patches Update Side By Side

The Official Runtime Catalog may refresh its small signed metadata, including ADR 0192 Runtime Trust Statements, automatically and create a **Runtime Update Candidate** without downloading payloads or changing the active environment. Unattended installation is eligible only for a host-computed **Runtime Security Or Compatibility Patch**: the source and target retain the same official trust root, package lineage, platform/architecture, declared runtime ABI/API and capability contract; introduce no new license acceptance, account, permission, network purpose, system modification, driver/kernel component, major backend or incompatible application/model requirement; and fit the governed download, temporary double-storage and verification budget. A publisher's version number, “patch” label, release note or remediation urgency alone cannot grant eligibility.

Under ADR 0483, automatic payload download/install also requires a still-valid, explicitly accepted runtime-maintenance policy covering the sources, patch class, network/storage budget and idle activation behavior. Initial setup consent alone does not enable later updates. With that policy and verified Unmetered connectivity, an eligible patch may download automatically from ADR 0189 governed sources into managed staging; otherwise it requires a reviewed update action. Revocation of the policy stops new automatic work without deleting installed packages. Metered, Roaming, Offline and Unknown retain ADR 0177 gates. Download and verification are resumable, content-addressed and non-active; failure, source outage or insufficient space leaves the currently active runtime unchanged. Automatic installation does not modify system Python/PATH, elevate privileges, keep the device awake, or bypass ADR 0176 power/thermal policy. It emits only ADR 0175 aggregate content-free progress and offers Pause/Resume from AI Environment Setup or AI Console.

The patch installs side by side under a new immutable Runtime Package identity. The host verifies signatures, monotonic trust/catalog state, manifest/digests, archive safety, platform signing where applicable, dependency closure and bounded synthetic readiness probes without reading user assets, model weights beyond already governed loader readiness, runtime databases or external services. The active runtime and every running/queued job keep their exact pinned environment while staging and verification occur; packages are never replaced in place.

Activation waits until no local AI execution, calibration, model load/unload, dependency transaction or result commit uses the affected runtime. New admissions pause at a bounded Local AI Resource Governor boundary, the candidate receives a final compatibility/health check, and Runtime Registry atomically switches the active package set. Activation may occur at an idle boundary or the next application launch, but never terminates an AI task merely to meet an update deadline. Jobs admitted after the switch use the complete new environment; one job cannot mix old and new libraries or executables.

The immediately previous verified package set becomes the **Last Known Good Runtime** and remains pinned through the ADR 0191 Runtime Rollback Window: exactly one previous set, a minimum 14-day plus three-Healthy-Start automatic-reclaim gate, and a 30-day unresolved-evidence notice rather than silent deletion. Startup failure, readiness regression, crash-loop evidence or failed post-switch health checks trigger bounded automatic rollback before new AI work is admitted, quarantine the candidate for that device/package identity and suppress retry storms until newer signed metadata or explicit repair. Manual rollback is available while retained and changes only future execution binding; it does not delete valid AI results or pretend different runtime/result provenance is equivalent.

A major version, new accelerator/backend family, changed runtime ABI/API or dependency capability, materially larger footprint outside the automatic budget, new/changed license, account, permission, network purpose, system component, reduced platform support or unproven compatibility creates a **Reviewed Runtime Update Plan**. It shows source/target identities, dependency diff, bytes and temporary storage, running/waiting impact, model/capability compatibility, derived-cache consequences and rollback coverage, and requires explicit confirmation. Splitting one major change into several packages cannot evade this review because eligibility is computed over the complete dependency closure.

Runtime patching never downloads, updates or selects model weights; ADR 0164 model updates remain user-triggered and side-by-side. It does not update Electron/application code; Release Flow retains application signing, update metadata and activation. A runtime patch may invalidate/rebuild explicitly declared Model Derived Runtime Cache entries, but cannot rewrite verified model artifacts, canonical results or ANN identity in place. Existing results retain exact model/runtime/recipe provenance.

The current repository has Runtime Package staging/execution, Runtime Registry and Local AI runtime status primitives, but no production remote candidate discovery, manifest-diff eligibility classifier, unattended payload policy, side-by-side runtime-set activation pointer, job/runtime pin drain, Last Known Good Runtime record, post-switch monitor or automatic rollback/quarantine loop. This ADR changes documentation only: it fetches no metadata/package, launches no runtime/model, reads no private storage or task data, and changes no public IPC/schema/AI Worker API.
