# Model Library Groups Variants And Deduplicates Blobs

Model Library presents a three-level identity: Model Family groups one architecture or product lineage, Model Checkpoint identifies one immutable trained checkpoint and semantic version/size, and Model Artifact Variant identifies one exact ADR 0161 manifest for a container, quantization, backend/runtime target, accelerator or platform form. Search and browsing default to family/checkpoint cards with expandable variants instead of presenting every GGUF, ONNX, safetensors and quantization file as an unrelated model. Active Capability Model still binds to one exact verified artifact variant and runtime evidence.

Hardware Variant Recommendation uses verified local platform, operating-system, architecture, available runtime/capability, accelerator, RAM/VRAM and disk evidence to rank compatible installed or catalog variants. It displays the reason, expected quality/resource tradeoff, missing evidence and whether the recommendation is only guidance. Unknown hardware or unavailable runtime produces Not Assessed rather than an inferred recommendation. A recommendation never downloads, installs, selects, starts or replaces a model automatically; the user may inspect and choose another compatible variant. ADR 0170 may compose recommendations into one reviewable four-capability plan and may reuse one exact artifact for multiple declared capabilities, while ADR 0171 defines profile-specific ranking and evidence labels; action still requires the plan's explicit Install And Enable consent.

Verified downloaded or ADR 0166 locally imported files are stored in an application-managed content-addressed Model Blob Store keyed by cryptographic digest. Model Artifact Manifests and local import records reference immutable blobs, so identical tokenizer, projection, vocabulary, configuration or weight bytes used by multiple variants occupy physical storage once. Package activation and removal update references transactionally, while startup/maintenance reconciliation repairs interrupted reference accounting without reading user assets or rescanning import sources. Sharing bytes does not merge manifest identity, publisher, acquisition method, ADR 0163 license acceptance or source-account scope, ADR 0165 trust/revocation/result-safety state, model-space identity or provenance. A critical statement scoped to a shared digest blocks every affected manifest reference without automatically deleting the blob. A user still accepts each package's current license even when an already-present blob avoids a download, while no credential is needed merely to reference already verified local bytes.

Model Library reports logical installed size, already-present shared bytes, additional download bytes, additional physical disk required and actually reclaimable bytes separately. Partial downloads are not active blobs. Uninstall removes one manifest reference and deletes a blob only when no installed or rollback-retained manifest, active load/job, verification transaction or required derived-cache build pins it. Shared bytes remain visibly attributed rather than being reported as reclaimed. Removing one variant never damages another manifest that references the same digest.

Model Derived Runtime Cache remains separate from immutable Model Artifact Storage and the Model Blob Store and may use a separate ADR 0167 Model Derived Cache Root. Compiled graphs, converted weights, backend kernels, runtime plans, repaired configuration and other reproducible derivatives are keyed by source manifest, exact variant, toolchain/runtime, platform/architecture, accelerator and build recipe. They may be budgeted and evicted when unpinned, then rebuilt, while installed verified blobs are never evicted as cache. Storage Management exposes model artifacts and model-derived cache as separate roots/classes and cleanup actions; Analysis Proxy Cache cleanup touches neither.

Different artifact variants are distinct Model Result Generations by default, including different quantization, container, custom runtime or backend implementations. Existing results remain usable with their original provenance under ADR 0143 and ADR 0145, but cannot be relabeled as generated by the newly selected variant. Cross-Variant Equivalence Evidence may unify generation semantics only for a named capability, checkpoint, input recipe, output schema, platform/runtime matrix and tested tolerance after deterministic fixtures prove weight/tokenizer/preprocessing identity, output behavior and confidence calibration. Marketing claims such as near-lossless or the same base model are not equivalence evidence.

Embedding variants use separate Active Embedding Spaces unless strict cross-variant fixtures prove vector dimension, normalization, distance metric, per-vector tolerance, nearest-neighbor ranking stability and query/asset symmetry for the declared runtime matrix. Without that evidence, vectors from different quantization, checkpoint, preprocessing or backend variants never enter one index or compare raw similarity scores. Selecting another embedding variant therefore follows ADR 0144 migration rather than silently reusing or mixing an index.

Installing another variant or ADR 0164 update does not automatically select it or reanalyze the library. Switching the active variant uses Model Activation Preview and affects future or explicitly migrated analysis according to ADR 0145; retained earlier results keep their exact artifact/runtime provenance. The immediately previous active variant stays blob-pinned through the visible rollback window. Variant uninstall preflight reports active assignments, rollback pins, result/index implications, shared versus reclaimable bytes, derived-cache impact and compatible installed replacements before any reference changes.
