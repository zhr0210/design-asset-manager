# Add Assets Requires Explicit Ownership And Fully Manages References

An active library exposes one neutral **Add Assets** entry rather than labeling every local-file action as import. After files or folders are selected and before reference scanning, transfer, or ownership commit, trusted application UI presents two explicit Asset File Ownership modes: **Copy Into Library** and **Reference in Place**. Copy Into Library is the visible, recommended, and preselected default for an ordinary Add Assets plan, including file and folder selections; the UI explains that the selected external sources remain untouched and requires confirmation of the reviewed copy plan before work begins. Reference in Place is an advanced alternative that must be explicitly selected for the current plan. The application cannot infer or change ownership from drag source, file type, source volume, prior use, available space, or a plugin suggestion, remember a mode invisibly, or switch modes after confirmation or failure.

Reference in Place admission leaves selected originals at their exact user-owned locations without copying, moving, renaming, rewriting, embedding metadata, or creating source-side control/cache files. After the normal real-format, safety, System Preview Ready, and reference-admission boundary, each successful item is a full Referenced Asset in Asset Workspace. ADR 0344 permits that item to contain multiple capability-declared member relationships under one Referenced Compound Original while preventing any physical source from simultaneously becoming a standalone/competing compound item in the same plan/library. It supports the same app-owned organization and discovery expected of other Design Assets: title and user metadata, tags, ratings, Collection Memberships, Smart Filters, lexical and semantic search, source browsing, preview, Compare View, OCR, descriptions, embeddings, AI analysis, external open, Original Handoff, and explicit relink/recovery where the relevant capabilities are available.

Full reference management also includes explicit **Referenced Source Operations** that may move or rename the user-owned original or rewrite its bytes through the application. A successful path operation updates the Referenced Asset relationship and Source Tree projection rather than creating another Design Asset or changing Asset File Ownership; a successful content rewrite follows Source Content Generation rules. Collection edits, Folder Collection Mapping, Source Tree selection or rearrangement, monitoring, analysis, and background reconciliation never imply one of these filesystem mutations. App-owned records, derivatives, and user-authorized source operations do not transfer ownership of the original bytes to the library, and the application still creates no source-side cache or control files merely because an asset is referenced. ADRs 0293 and 0294 separate deletion authorities and resolve source-delete item commit, failure, interruption, and batch behavior. ADR 0301 treats same-volume relocation as a path-only operation and cross-volume transfer as an explicitly confirmed copy, complete verification, then old-source trash sequence; ADRs 0302 through 0318 resolve its partial-success, collision, recovery, undo and batch boundaries. ADR 0319 separately governs capability-supported staged content rewrite without turning metadata edits or Compatible Export into source mutation. Those commands remain single-file contracts. ADR 0345 instead moves a Referenced Compound Original only through one complete group path plan, ADR 0346 deletes its sources only through one complete group delete intent and member receipt set, and ADR 0347 rewrites it only through one whole-group candidate validation and generation commit. ADR 0348 keeps cross-format output source-separated, while ADR 0351 handles complete single-file or compound Asset File Ownership conversion as a separate explicit workflow and ADR 0357 prevents that conversion from becoming implicit metadata writeback.

Copy Into Library leaves the selected external source untouched, enters the ADR 0106 Capture Gateway/Candidate lifecycle, validates and copy-verifies complete bytes, and commits the destination under ADRs 0280 through 0291 before Candidate Activation. The destination is library-owned and follows Candidate/Managed Asset backup, retention, Asset Trash, and permanent-deletion rules; the external source never becomes a second library-owned copy or a future cleanup target merely because it supplied those bytes. ADR 0335 makes a local-file copy selection a reviewed plan followed by progressive, item-committed Candidate Intake rather than one all-or-nothing import transaction.

Reference in Place is also distinct from ADR 0275 In-Place Reference Library adoption. Adoption creates the portable Library Root/control boundary around an existing directory during Library Start; Add Assets attaches an ordinary file/folder source to an already active library. Both preserve user ownership and may share validation/indexing capabilities, but one cannot silently create, relocate, or replace the other's library boundary.

Browser, download, clipboard, Local Capture API, and capture-plugin acquisitions remain managed Candidate Intake under ADRs 0106 and 0280; they do not offer Reference in Place because no stable user-owned local original has been selected as that relationship. The current application has no production Add Assets ownership sheet, portable referenced-source model, progressive local reference admission, Referenced Source Operation workflow, or ownership-aware import gateway, and its current asset rows do not implement this target distinction. This ADR records target architecture only and selects, scans, copies, moves, rewrites, imports, references, or deletes no runtime/user file and changes no public IPC, database schema, or AI Worker API.

file/image/asset payload on a Text field is rejected rather than importing it,
selecting ownership, inserting a path or creating a relationship; only a
