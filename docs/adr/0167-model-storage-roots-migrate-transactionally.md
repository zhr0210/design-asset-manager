# Model Storage Roots Migrate Transactionally

Users may place managed model data on an internal or removable local volume through a Model Storage Root. The root owns Model Artifact Manifests, Model Blob Store files, reference/rollback state and transaction journals; it is a destination and accounting boundary, never a watched import directory. Model Derived Runtime Cache may use a separate Model Derived Cache Root because it is rebuildable and has different cleanup semantics. Analysis results, embedding indexes, user assets and library metadata do not move merely because model storage moves.

Every managed root carries an application-created Model Storage Identity, schema/layout version and integrity metadata bound to the configured root record. A display path, volume label, drive letter, mount point or same directory name is not identity. Public UI shows a user-readable volume name, capacity, availability and abbreviated opaque identity without exposing full paths. The official build initially supports only local filesystems whose macOS/Windows adapter proves required file-size, write, locking, atomic-commit, durability, case/collision, symlink and permission behavior; network or otherwise unverifiable filesystems remain Incompatible rather than presumed safe.

Changing either root uses a Model Storage Migration Plan under ADR 0003 principles: dry run, explicit confirmation, durable journal, rollback and no automatic path rewrite. Preflight reports source/destination identities, logical and physical bytes, shared blobs, derived-cache bytes, rollback-pinned artifacts, active assignments/jobs/downloads/imports, target free space plus Storage Safety Reserve, temporary double-storage requirement, filesystem capability evidence, expected resumability and items that cannot move. Selecting a directory does not switch active storage.

After confirmation, migration blocks new downloads, updates, imports, activation changes and derived builds; it pauses or safely completes model jobs, unloads affected models and releases file pins. Same-volume migration may use verified copy-on-write optimization, while cross-volume migration copies into destination staging. Every manifest, reference record and immutable blob is copied and verified against its expected digest; derived cache may be copied with toolchain keys and validation or omitted as explicitly rebuildable. No user asset or analysis result is opened to validate a model-storage migration.

Only after destination inventory, full blob verification, journal reconciliation, permission checks and a bounded no-user-asset readiness check pass does the registry atomically commit the new root identity. A failed or interrupted migration resumes from its journal or rolls back to the unchanged source root; it never leaves a partially copied destination advertised as active. The prior root remains a read-only rollback source through a visible cleanup decision. Removing its managed copy requires a second explicit confirmation after the new root is active and reverified, and deletion is constrained to the recorded old managed root; unrelated files and ADR 0166 import sources are never removed.

If an active removable Model Storage Root disappears, its artifacts become Model Storage Unavailable rather than uninstalled, corrupt or deleted. New loads and affected ADR 0168 Analysis Intents wait with the typed storage reason; an already configured compatible model on another available root may participate only through the normal Capability Fallback Chain. The application does not create waiting image proxies, redownload, re-import, change Active Capability Model, delete derived records, remove results/indexes or scan other volumes to find similar files. Non-model library and non-AI workflows remain available.

Reconnect verifies expected Model Storage Identity, root schema, transaction state, manifest/reference consistency and trust state before restoring availability. Active or requested blobs receive full digest verification before load, and a bounded background audit verifies remaining blobs; changed or missing blobs stay unavailable until repair/reimport rather than being trusted from path continuity. A different volume mounted at the same path or drive letter becomes Wrong Storage Identity. Read-only, insufficient-space, interrupted-transaction and incompatible-filesystem states remain distinct and expose repair, migrate or disconnect actions without paths.

If only Model Derived Cache Root is offline, installed artifacts remain available when their required runtime can rebuild derivatives elsewhere under an explicitly selected compatible cache root; otherwise the affected optimized route is unavailable without redownloading model blobs. Cache cleanup, cache relocation and artifact-root migration use separate accounting and consent. Model Storage Management reports immutable artifact bytes, shared bytes, rollback pins, derived cache, partial staging, unavailable roots and actually reclaimable bytes without merging any of them into Analysis Proxy Cache.

Current settings containing raw model paths or a single modelRootDir require a later compatibility migration into opaque root/artifact identities. Until that migration is implemented, existing paths are legacy implementation details and cannot be presented as satisfying this ADR. No automatic conversion, source deletion or runtime database rewrite follows from this documentation decision.
