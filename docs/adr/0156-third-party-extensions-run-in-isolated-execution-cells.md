# Third Party Extensions Run In Isolated Execution Cells

Scope: Target architecture, refined by [ADR 0484](0484-extension-contracts-and-deferred-agent-development-access.md)
and the AI+ core boundary in [ADR 0483](0483-ai-plus-core-product-and-extension-boundaries.md).
The full ecosystem below is not a prerequisite for core product work; selected public
capabilities must satisfy their applicable contracts before third-party execution.
No SDK, catalog or sandbox is delivered merely by this decision.

Third-party extension code never loads into the Electron main process, the primary React renderer, a preload bridge, or the Extension Host itself. Extension Host is a trusted supervisor and permission broker only. It validates manifests, negotiates Extension API and worker protocol versions under ADR 0159, resolves ADR 0160 public capability bindings, computes Effective Permission Sets, creates bounded handles, routes structured messages, enforces quotas, and terminates work. Each plugin identity executes in its own Extension Execution Cell so one plugin cannot share globals, modules, writable code, memory, credentials, handles, private storage, or a crash boundary with the application or another plugin. The retired internal SitePlugin and BrowserExtractorPlugin interfaces were not execution cells or public compatibility surfaces.

Inspector Panel Contributions use an Isolated Extension UI owned by the application: a sandboxed renderer surface with context isolation, no Node or Electron access, no main-renderer store imports, no main DOM injection, a restrictive content policy, blocked arbitrary navigation and window creation, and an app-owned message bridge limited to the declared Extension UI Slot. Extension UI cannot contact the network directly; approved requests go through Extension Host so declared hosts, purposes, credentials policy, byte limits, cancellation, and audit state remain enforceable. A panel crash or unload destroys only that plugin surface.

Command, capture, analysis, and portable compute code runs in a dedicated Extension Worker Process or an equivalently isolated per-plugin worker boundary launched by a platform confinement adapter. Native and format workers run as declared executables started by the trusted host, not as arbitrary commands supplied at runtime. The cell receives a minimal environment without application secrets, user credentials, private IPC names, or unrestricted host paths; the installed package is read-only, task input staging is read-only, derived output staging is write-only, and all other asset-library, database, model-cache, home-directory, process, and network access is denied. V1 workers cannot launch undeclared descendants, elevate privileges, attach to application processes, or keep staged handles after task completion.

An extension capability is Available on a platform only when its Platform Confinement Evidence proves the required filesystem, network, process, message, resource, cleanup, and crash-containment behavior for that package kind and Native Extension Target. The implementation may use different macOS and Windows confinement adapters while returning the same public capability and incompatibility shape. A missing, failed, or unverifiable API/protocol/ABI match or isolation mechanism makes the contribution Incompatible or Unavailable in the official build; a signature, catalog review, user permission grant, or successful launch cannot substitute for compatibility or confinement evidence. Developer Mode retains the same execution cells and marks any technically unavoidable weakening explicitly rather than claiming production compatibility.

Extension Host enforces per-cell time, CPU, memory, disk, output, message, concurrency, recursion, and restart limits. A crash, timeout, malformed protocol response, output validation failure, forbidden access, or attempted capability escape consumes a versioned Extension Failure Budget and becomes a structured path-free failure attributed to the plugin and operation. The host terminates the affected cell, invalidates its handles, removes task staging, and preserves the application, other plugins, originals, prior valid results, and plugin-owned user data.

Exhausting the failure budget or detecting a severe isolation violation places the plugin in Extension Quarantine. Quarantine disables its contributions, prevents automatic restart, and exposes the reason, affected capability, last safe diagnostic summary, update/repair/uninstall actions, and an explicit user-controlled probationary re-enable when ADR 0158 trust state permits. Re-enable starts a fresh cell with no previous handles; another qualifying failure can quarantine it again. Updating, reinstalling, granting permissions, paying for a plugin, or restarting the application does not silently clear quarantine unless the verified lifecycle policy explicitly resolves the cause, and Critical Security Revocation has no probationary override. Logs and telemetry remain content-free and exclude asset pixels, extracted text, credentials, private paths, staged payloads, and plugin storage values.
