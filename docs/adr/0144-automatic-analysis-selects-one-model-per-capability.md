# Automatic Analysis Selects One Model Per Capability

Each automatic analysis capability selects one Active Capability Model rather than running every installed model. Under ADR 0168, ordinary automatic intents remain capability/generation scoped and bind the exact active artifact only when execution admission succeeds; changing the active model does not enqueue already completed historical assets. Tagging, OCR, captioning, embedding, and future capabilities may each choose a different primary local model, but one capability has one automatic primary model and version at a time. ADR 0170 may assign these primaries together only through its explicit reviewed Install And Enable consent and only after each dependency chain verifies. Existing content-routed RAM, Florence-2, WD Tagger, CLIP, and rule pipelines remain available for explicit enhanced or manually selected analysis; they do not justify automatic multi-model fan-out for every asset. Deterministic non-model rules may supplement a capability only when their provenance remains distinct.

A Capability Fallback Chain may name ordered compatible local alternatives for tagging, OCR, or captioning. Fallback runs only when the primary capability is unavailable, receives an ADR 0165 execution block, or returns a structured eligible failure, never merely to increase result count. A trust-triggered fallback uses only an already installed, configured, compatible and non-revoked local alternative and never downloads, selects or migrates a replacement. Evidence records selected primary, actual model, fallback reason, model and recipe version, and confidence semantics. Results from different models are not assigned comparable confidence without explicit calibration. External providers never participate in automatic fallback under ADR 0141.

Model identity is distinct from Execution Backend and includes the verified Model Artifact Variant and Manifest under ADR 0161 and ADR 0162 rather than a mutable repository name or direct local path. ADR 0166 Unverified Local Models cannot become Active Capability Models until exact declarative identity needed by an approved loader and a safe readiness probe exist; probe success alone does not invent missing provenance or equivalence. PyTorch, ONNX Runtime, Core ML, CUDA, DirectML, MPS, CPU, or another backend may execute the same declared checkpoint only when Cross-Variant Equivalence Evidence proves weights, tokenizer or vocabulary, preprocessing, output dimension, normalization, output behavior, confidence semantics and fixture tolerances compatible for that capability. A backend or quantization change with unproven equivalence creates a distinct model/result generation. Backend selection may optimize the current platform without changing the shared capability contract or silently changing the embedding space.

Semantic search has exactly one Active Embedding Space for ordinary library search. Its identity includes image and text checkpoint/artifact variant, tokenizer, input recipe, vector dimensions, normalization, distance metric, index schema and runtime equivalence evidence. Asset vectors and query vectors must share that identity; vectors from CLIP, SigLIP, different checkpoints, quantizations, incompatible preprocessing, or unproven backend outputs are never inserted into one comparable index or averaged across spaces.

Changing the active embedding model creates an Embedding Space Migration. The current complete index remains active while a separately namespaced target index is rebuilt through resource-aware background work. Search never compares raw scores across the two spaces. The target becomes active atomically only after its declared eligible-asset coverage and validation gate pass; interrupted, capability-unavailable, or storage-paused migration leaves the prior index usable. New or changed assets receive the active-space vector and may additionally receive the target-space vector while migration is in progress, without treating either as an image-input cache.

Users may explicitly run additional local models for selected assets, units, views, or batches. Those results enter View-Level Analysis Evidence with their own model provenance and can participate in ADR 0140 projections only through declared calibration or aggregation rules. Additional embeddings remain in separate model-space namespaces and affect ADR 0181 ordinary hybrid search only after an explicit active-space switch; raw scores from separate spaces are never fused. A manual multi-model action does not change the library default, install models, or authorize external upload. Model artifact lifecycle belongs to ADR 0152's Model Library, while upgrades and existing-library reanalysis remain separate explicit operations under ADR 0145.
