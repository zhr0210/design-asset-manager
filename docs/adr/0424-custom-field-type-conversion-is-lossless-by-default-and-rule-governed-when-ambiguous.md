# Custom Field Type Conversion Is Lossless By Default And Rule-Governed When Ambiguous

Custom Field Type Migration must produce the same disclosed result across devices rather than inheriting locale, language or timezone guesses. A value is eligible for direct batch confirmation only through a **Lossless Custom Field Conversion** whose target value is unique, preserves the complete source meaning and requires no precision, format, timezone or option-choice assumption.

A conversion requiring date parsing/format, timezone or offset assignment, number precision or rounding, select-option choice, truncation or any other potentially lossy interpretation is a **Rule-Governed Custom Field Conversion**. The user must select the explicit conversion rule before commit, and ADR 0423 Custom Field Type Migration Preview must show representative before/after examples plus affected, convertible and retained-unconvertible counts under that rule. Merely opening the preview or selecting a target type grants no conversion authority.

The application never chooses a rule from the operating-system language, locale, region, current timezone, display formatting or whichever parser accepts a value first. Under ADR 0435, an exact Number target must fit the finite Decimal128-equivalent domain and current range constraints without implicit precision loss; display precision, grouping and unit labels provide no conversion rule. Under ADR 0436, creating or comparing a Known-Instant DateTime requires explicit offset evidence, and an Unzoned value remains Unzoned unless a reviewed rule assigns a zone and resolves daylight-saving ambiguity. ADR 0437 additionally requires explicit normalization for missing seconds and a reviewed rounding/truncation rule above nine fractional digits. Under ADR 0440, a Text target may undergo Unicode NFC canonicalization but must fit the active grapheme limit without implicit trimming, whitespace collapse, case change or truncation. ADR 0441 requires the preview to disclose when a conversion yields Missing zero-length Text rather than a target value, while non-empty whitespace-only Text remains an exact present target. ADR 0442 rejects ill-formed Unicode and unsafe controls without silently stripping them while preserving valid invisible formatting with a visible warning. ADR 0443 also requires any present target to satisfy the target field's minimum and versioned pattern without parser-specific fallback. A value that remains ambiguous, violates the chosen rule or cannot produce a valid target value is an **Unconvertible Custom Field Value** and stays on the source field without default substitution, clearing, partial parsing or guessed option mapping.

This ADR establishes conversion safety classes rather than omitting difficult type pairs. ADR 0425 covers every directed ADR 0417 type pair through lossless, rule-governed or manual mapping without an implicit Text/intermediate conversion. ADR 0428 may preserve an explicitly selected rule as reusable library intent but never as prior confirmation or a device-derived default. Each pair's exact built-in lossless conditions and available explicit rules remain dependent decisions.

ADR 0462's Number Input Locale belongs only to interactive manual entry. It is
not a Custom Field conversion rule and cannot resolve an ambiguous Text-to-
Number, URL-to-Number or imported numeric literal during migration merely
because the same string would parse in the current editor.
