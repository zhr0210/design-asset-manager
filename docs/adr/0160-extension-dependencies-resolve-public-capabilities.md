# Extension Dependencies Resolve Public Capabilities

Scope: Target architecture, refined by [ADR 0484](0484-extension-contracts-and-deferred-agent-development-access.md)
and the AI+ core boundary in [ADR 0483](0483-ai-plus-core-product-and-extension-boundaries.md).
The full ecosystem below is not a prerequisite for core product work; selected public
capabilities must satisfy their applicable contracts before third-party execution.
No SDK, catalog or sandbox is delivered merely by this decision.

Extension API v1 does not allow one plugin to import, link, address, invoke, install, activate, or depend on another specific plugin identity. Plugins cannot discover another plugin's process, UI, commands, private RPC, package files, handles, globals, memory, credentials, or Namespaced Extension Storage. The public dependency contract is an Extension Capability Requirement with a stable capability identifier, compatible contract/version range, required or optional level, and any declared platform or fidelity constraints. It describes what is needed, not which publisher or package must supply it.

Built-in application capabilities and verified Format or Model Runtime Capability Packs under ADR 0161 publish Extension Capability Offers through the same versioned capability registry. Extension Host creates a recorded Extension Capability Binding only after the requirement, offer, Extension API/worker protocol, platform/native target, trust state, permissions, confinement evidence, health, and current context are compatible. A consumer communicates only through the public capability contract and operation-scoped handles; it cannot observe or rely on the provider's implementation identity. When multiple offers qualify, an explicit user preference wins, then a compatible built-in default; if only multiple third-party choices remain, Extension Library asks the user rather than silently granting one publisher authority.

A missing required offer produces Dependency Unsatisfied and disables only the dependent contribution. The plugin package, independent contributions, storage, prior results, and provenance remain intact. An optional requirement reports reduced capability or fidelity and follows its declared fallback without claiming the missing feature. Provider crash, quarantine, revocation, permission loss, incompatibility, or uninstall invalidates affected bindings and returns structured dependency evidence instead of crashing the consumer or leaking a provider handle.

One-click installation may propose a Dependency Install Plan containing the requested extension plus compatible capability packs or Managed Shared Runtimes. ADR 0170 Local AI Starter Setup uses the same bounded capability-dependency expansion for its displayed model assignments without merging model and extension package identities. Before any download, the trusted application expands the complete bounded closure and displays every package, publisher, version, purpose, required/optional status, installed and download size, license, permission, native/external execution, restart, trust source, provider choice and ADR 0177 Network Cost Evidence. The user can cancel the plan or omit optional items. Required items cannot be hidden behind a single size, license or traffic summary. No plugin may start a package download at runtime, and the resolver rejects cycles, unknown providers, unbounded ranges, incompatible targets, conflicting requirements, excessive depth/size, or any graph it cannot fully explain before consent.

Managed Shared Runtime artifacts are host-installed, content-addressed, verified, immutable and mapped read-only only when the execution cell's confinement evidence permits it. Sharing identical immutable bytes does not share a process, writable code, globals, memory, handles, caches, credentials, or private storage. Incompatible required runtime versions remain side by side when policy and disk budget permit; a mutable global runtime is never upgraded underneath active plugins. Native libraries are not loaded into Electron or Extension Host and still execute behind the provider's declared isolated worker boundary.

Uninstall and update preflight compute a reverse capability-impact graph. Before removing or changing a provider, Extension Library lists affected plugins and contributions, active jobs, available compatible alternatives, storage impact, and whether a new permission or download would be required. The user may cancel, choose an alternative, or proceed with dependent contributions becoming Dependency Unsatisfied; the application does not cascade-uninstall consumers or delete their data. Automatic rebinding is allowed only to the same already-approved built-in capability or a previously user-selected compatible offer with no expanded permission or trust scope, and the new binding remains visible in provenance.

The existing internal Runtime Package manifest may continue to use concrete package IDs for the application's controlled AI/runtime installation graph. That private resolver is not the Extension API dependency ABI and cannot let third-party packages name arbitrary internal packages. Extension catalog schemas, SDK fixtures, compatibility preflight, admission review, and uninstall tests validate capability requirements and offers independently from internal Runtime Package entries.
