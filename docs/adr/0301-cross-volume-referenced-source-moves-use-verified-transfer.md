# Cross-Volume Referenced Source Moves Use Verified Transfer

Moving or renaming a Referenced Asset's user-owned original within the same verified physical volume is **Relocate Referenced Source**. After validating the expected source, safe unoccupied destination and filesystem boundary, the application performs a path-only move and revalidates the result before committing the referenced-source relationship and Source Tree projection. Stable byte identity preserves the same Design Asset, Source Content Generation, user metadata, derivatives and Asset File Ownership; ADR 0311 routes a destination collision to visual Relocation Conflict Review rather than handling it automatically, and a failed or ambiguous operation never creates another Design Asset or guesses a path.

A destination on another physical volume cannot be presented or journaled as the same operation because it is physically copy plus deletion rather than a filesystem rename. **Transfer Referenced Source Across Volumes** therefore requires a separate confirmation that identifies this consequence, copies to the selected destination volume, verifies the complete destination bytes against the current Source Content Generation, and only then requests moving the old source to operating-system trash. Exact verified bytes preserve the same Design Asset and Source Content Generation, and the destination remains user-owned referenced content rather than becoming Copy Into Library or a Managed Asset. No path update, old-source deletion, ownership conversion, format conversion, metadata merge, automatic filename change or fallback may be inferred from a partial or failed copy. ADR 0302 preserves the verified destination and records truthful partial success when only the final old-source trash request fails; ADR 0303 prevents partial destination bytes from becoming a visible source and makes only proven operation staging resumable or removable; ADR 0304 allows reviewed unique-name or replacement choices without permitting silent collision handling; ADR 0310 retains device-local recovery evidence only after old-source trash succeeds.

Both operations require durable intent and item-scoped reconciliation because process interruption, volume removal, permissions and nonlocal filesystems may make the observed result ambiguous. ADR 0309 rejects post-success whole-transfer undo: moving back is a new Transfer Referenced Source Across Volumes with fresh evidence and confirmation. ADR 0312 resolves post-trash relocation-replacement recovery, while ADR 0313 gives only simple successful same-volume moves a short verified reverse-relocation affordance. ADR 0314 resolves batch commit and conflict isolation, ADR 0315 limits batch undo to independently revalidated simple same-volume relocations, ADR 0316 stops only unstarted or safely checkpointed pre-publication batch work, ADR 0317 serializes active batch path operations per involved physical volume, and ADR 0318 permits only bounded evidence-stable pre-publication automatic retry. ADR 0319 keeps byte-changing Rewrite Referenced Source separate from both path operations. These path operations remain single-file contracts: they cannot target a Referenced Compound Member Relationship or interpret a primary-member move as authority over companions. ADR 0345 provides the separate complete group plan, journal and relationship commit required to move a Referenced Compound Original. The current application has no Referenced Asset ownership model, same-volume relocation, cross-volume source transfer, operation journal or Source Tree mutation pipeline. This ADR records target architecture only and accesses, copies, moves, renames, deletes or writes no runtime/user file and changes no public IPC, database schema or AI Worker API.
