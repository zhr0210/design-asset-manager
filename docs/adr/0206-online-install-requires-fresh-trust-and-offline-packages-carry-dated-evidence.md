# Online Install Requires Fresh Trust And Offline Packages Carry Dated Evidence

Online Model Catalog and Official Runtime Catalog installation or update requires **Fresh Trust Install Admission** for every affected trust root/channel. A Last Verified Model/Runtime Trust State within ADR 0204's 24-hour freshness window satisfies the gate. If it is stale or Trust Not Assessed, the application first performs a bounded signed Trust Catalog refresh; failure leaves the reviewed transaction in **Waiting For Fresh Trust Metadata** and transfers or promotes no new online model/runtime payload. Cached catalog entries may remain browsable with their visible freshness, but browsing, selecting or approving a plan cannot treat stale metadata as current.

The preflight refresh retrieves metadata only and does not itself authorize package bytes. After it succeeds, ordinary model/runtime plan, license, account, network-cost, storage, compatibility and user-consent rules still apply. A long-running transfer whose admission evidence becomes stale before atomic promotion must reverify current trust metadata before making the artifact installed/active; verified staged bytes may remain managed and non-executable while waiting. A refresh failure never deletes a working installed artifact, clears a known revocation or causes an external-inference fallback.

ADR 0221 applies the same gate to Official Package Reacquisition after Digest Mismatch. Review may identify the exact signed candidate while stale, but payload transfer waits for fresh accepted trust metadata and never uploads or adopts the mismatching actual digest.

An Official Offline Model/Runtime Package or ADR 0188 Offline Full Installer remains usable without network access. It must carry an immutable package manifest, exact file identities/sizes/digests, publisher/trust-root identity, platform/architecture and compatibility bounds, required license evidence, and a signed **Dated Offline Trust Evidence** snapshot with issue time and monotonic statement sequence. The current signed application independently verifies every signature, trust chain, sequence, manifest binding, digest, archive boundary and compatibility rule before staging or installation. A platform/application signature around a container does not replace its inner package and trust verification.

ADR 0218 presents the selected basename/actual size separately from these signed fields in a session-bound External Package Identity Card. Missing or failed evidence remains visibly unverified rather than being inferred from the external filename, while a digest abbreviation is comparison-only and never replaces full verification.

Offline evidence is compared with persisted Last Verified Trust State before use. An older bundle/snapshot cannot roll back a newer statement, clear or narrow an accepted revocation/suspension, or install a digest already blocked by known trust evidence. Applicable known revocation blocks installation. In the absence of a known block, an exactly verified official offline package may install while the UI prominently shows the evidence issue date and current freshness rather than claiming that the device checked the latest online state. Later online refresh reconciles monotonically and does not reinstall, activate, replace or remove the package by itself.

ADR 0207 gives Dated Offline Trust Evidence no arbitrary 90/180/365-day expiration. Evidence age remains visible, while new installation blocks only for a typed signature/trust-chain, explicit signed validity-period, compatibility, known root-revocation or known package/model/runtime-revocation failure. Evidence aging after successful installation is not itself an execution revocation.

When a package declares an explicit signed installation-time boundary, ADR 0208 requires Trusted Current Time Assessment. Time Not Assessable blocks only that new time-bounded offline installation and offers no Continue Anyway; it does not convert every undated offline package into an online dependency.

Offline transport does not change product consent. Baseline runtime activation follows ADR 0188 Bootstrap; model selection and capability assignment remain explicit under ADRs 0152/0170; updates remain side-by-side under ADRs 0164/0190. The bundle is not a permanent catalog, does not authorize unrelated payloads and does not create automatic model selection, result migration or reanalysis.

An unsigned file, unknown signing key, arbitrary GitHub release/repository, copied framework cache, nearby manifest/README or third-party package cannot enter the Official Offline Package lane. Locally selected declarative model files follow ADR 0166 and remain Unverified Local Model unless their complete bytes exactly match acceptable signed catalog evidence. Future explicit third-party catalogs use their own user-approved trust roots and visible publisher identity; they never inherit Official Catalog status or bypass official critical digest blocking merely by being signed.

Status and diagnostics expose opaque plan/package/trust identities, freshness, evidence issue date and typed waiting/blocking reasons only. They do not expose local source paths, raw URLs, credentials, archive entries, model names from private catalogs, user assets/results or private verification logs. The current project has no Fresh Trust Install Admission, Waiting For Fresh Trust Metadata state, signed offline trust snapshot schema, monotonic offline/online evidence merger or offline package importer. This ADR records target behavior only: it refreshes/downloads/installs nothing, reads no package/model/cache/asset/result/private state and changes no public IPC/schema/AI Worker API.
