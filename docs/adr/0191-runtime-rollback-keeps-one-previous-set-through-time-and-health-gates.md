# Runtime Rollback Keeps One Previous Set Through Time And Health Gates

After ADR 0190 activates a new runtime set, Runtime Registry pins exactly one coherent immediately previous **Last Known Good Runtime**. It is not eligible for automatic reclamation until both gates pass: at least 14 elapsed days since successful activation and at least three distinct **Healthy Runtime Starts** of the new active set. A Healthy Runtime Start requires one completed application/runtime activation session with the full active-set identity, bounded synthetic readiness checks and no startup failure, crash-loop, automatic rollback or package-integrity fault. Automated crash restarts and repeated probes inside one session do not inflate the count.

Clock rollback, missing timing evidence, registry recovery or an unclean transition cannot shorten the 14-day floor. Runtime Registry retains activation time, health-count evidence, last health time and current rollback eligibility as path-free state. If the time and health gates pass, the previous set becomes **Runtime Rollback Reclaimable** and ordinary managed maintenance may release it without an additional modal confirmation while reporting the actual reclaimed bytes. The user may keep it longer through a visible pin; clearing that pin restores ordinary eligibility rather than deleting immediately during an active operation.

If 30 days elapse and the new set still lacks three Healthy Runtime Starts, the application keeps the previous set and surfaces one non-blocking Storage Management/AI Console action. It does not silently reinterpret elapsed time as proof, repeatedly nag at launch or delete the rollback set. The notice shows missing health evidence, rollback-pinned physical bytes and choices to run a bounded health check, keep the rollback set, or explicitly reclaim it with the resulting loss of local rollback. A user-confirmed early reclaim is allowed only after current-set integrity/readiness preflight and never occurs as a side effect of generic cache cleanup.

Low-disk pressure may recommend early reclaim and may prevent a new unattended update whose staging plus rollback would consume the Storage Safety Reserve, but cannot automatically delete the only Last Known Good Runtime before the two gates pass. A Reviewed Runtime Update Plan may offer an explicit reduced-recovery choice after showing temporary and retained bytes; an unattended patch blocks/waits instead. The application never deletes originals, model artifacts, analysis results, canonical embeddings or required previews to create runtime rollback space.

Runtime packages and dependencies are immutable and referenced by digest so identical bytes shared by active and previous sets occupy physical storage once. Storage Management reports logical active size, logical rollback size, shared bytes, rollback-only physical bytes and actually reclaimable bytes separately. Runtime-derived caches remain reproducible and are not pinned merely because a prior runtime set is retained; rollback may rebuild compatible derivatives. Active jobs, verification/install transactions, offline source imports and another declared owner can independently pin bytes after the rollback window ends.

ADR 0222 Awaiting Install Decision or Kept Verified Package Copy is another declared package-byte owner, not an installed or rollback set. Deleting that copy drops only its reference and reports physical reclamation after active/rollback/transaction/other-copy owners are considered; it cannot remove bytes still pinned for execution or rollback.

ADR 0223 may expire the Awaiting Decision owner after seven days, while an explicit Kept Verified Package Copy Pin remains until user-reviewed unpin/delete or installation reclassification. Neither transition changes Last Known Good Runtime eligibility, and shared bytes remain while any active/rollback owner exists.

ADR 0224 may extend only that pending owner with one missed-warning grace; it never extends, shortens or changes active/Last Known Good rollback pins, and physical bytes remain deduplicated across all owners.

ADR 0225 atomically changes only a Kept Verified Package Copy owner into a new pending-decision owner. Unpin is not deletion, does not change rollback eligibility and cannot release shared bytes while an active or Last Known Good Runtime owner still references them.

ADR 0226 may block creation of a new Keep owner when its newly protected physical bytes would create or enlarge a Storage Safety Reserve shortfall. It cannot count Last Known Good Runtime bytes as an ordinary deletable managed-copy candidate, release an existing rollback/Keep pin automatically or change either owner's eligibility; any early rollback reclaim remains the separate reviewed action in this ADR.

ADR 0242 may identify this rollback owner as blocking advanced deletion of an ambiguous recovery-protected managed copy and route back to this governed surface. That route grants no early-reclaim authority: health/time gates, current-set preflight and explicit release remain unchanged, and the recovery page cannot force or preselect rollback removal.

On a later successful activation, the formerly active verified set becomes the one new Last Known Good Runtime and the older rollback set loses its rollback pin atomically, preserving the “one previous set” limit. The update cannot rotate the pin unless the outgoing active set is internally complete and verified. ADR 0192 current Runtime Trust State participates in every rollback decision: a package with critical revocation or known integrity failure is never presented as Last Known Good; if no safe compatible previous set exists, the UI states that rollback is unavailable rather than retaining or executing known-unsafe code.

Manual or automatic rollback changes the runtime binding for future AI execution and resets update health evaluation; it does not relabel/delete results, modify models or restore evicted derivatives as authoritative data. ADR 0185 Full Library Backup continues to exclude runtime package payloads and rollback copies while recording dependency identities needed to reacquire compatible packages.

The current project has no coherent runtime-set activation/rollback record, elapsed/clock-anomaly gate, Healthy Runtime Start counter, rollback byte-reference accounting, 30-day unresolved prompt or automatic reclaim eligibility. Runtime Registry package metadata and general storage reporting are only implementation inputs. This ADR changes documentation only: it reads/deletes no runtime package/cache/private data, runs no health check/model, and changes no public IPC/schema/AI Worker API.
