# Runtime Trust Revocation Stops Execution Without Silent Fallback

The Official Runtime Catalog distributes signed monotonic **Runtime Trust Statements** scoped to trust root, publisher/source, Runtime Package Manifest and digest, complete runtime-set/dependency identity, platform/architecture, ABI/API and affected capability/model execution binding. A statement carries a strictly increasing sequence, response class, reason category, issue/freshness metadata, affected execution scope and remediation identity. The application persists Last Verified Runtime Trust State, rejects sequence rollback and requires a newer signed recovery statement to clear or narrow an accepted revocation or suspension.

**Critical Runtime Security Revocation** covers supply-chain compromise, malicious/substituted executable content, sandbox or capability escape, credential/data exposure, exploitable loader/parser/runtime behavior or another confirmed severe issue requiring containment. Once accepted, it immediately blocks the affected environment from new Bootstrap promotion, activation, readiness probing with affected code, model loading and AI job admission. There is no continue-anyway control in the official build, Developer Mode, offline mode, alternate mirror or second catalog that can execute the same revoked digest/identity.

An affected running job is cancelled at the earliest bounded containment boundary and its incomplete output/staging is discarded. If waiting for an ordinary unit boundary would prolong an active privacy, credential or execution escape, the host terminates the isolated runtime process immediately, marks the unit interrupted and still commits no partial result. Unaffected runtime cells/capabilities and the non-AI asset manager continue. Existing queued intents enter a typed **Waiting For Safe Runtime** state rather than retrying or failing repeatedly.

The host first evaluates an already installed compatible, verified and non-revoked Last Known Good Runtime or capability binding. It may atomically roll back only when exact compatibility and current trust evidence pass; age or prior “known good” labeling cannot override a current statement. If the signed remediation is an ADR 0190 Runtime Security Or Compatibility Patch, governed Unmetered automatic download/install may proceed only within the explicit maintenance policy required by ADR 0483/0190; otherwise remediation needs reviewed consent. A remediation that changes license, permission, account, system component, major backend/API or another reviewed boundary remains a Reviewed Runtime Update Plan even during an incident. Security urgency cannot manufacture consent or weaken package verification.

When no safe installed or downloadable remediation exists, the affected AI capability remains unavailable with a path-free reason, affected scope, trust freshness and recovery entry point. The application never sends an asset to an external AI provider, selects/downloads a model, changes capability assignments or installs a system driver as fallback. Original assets, previews, metadata, lexical search, unaffected local capabilities and already stored results remain available according to their own contracts.

Execution revocation and historical result validity do not conflict. A Runtime Trust Statement has no authority to delete, relabel, quarantine, hide, de-rank or remove committed tags, OCR, descriptions, palettes, embeddings or indexes from active projections/search. Those results retain their exact producing runtime/model/recipe provenance and ordinary ADR 0143 manual lifecycle controls. Separate model/output correctness evidence, if any, belongs to the ADR 0165 model-analysis domain and is never inferred from a runtime security declaration. The managed revoked package remains non-executable and explicitly removable rather than being silently deleted, preserving identity for explanation and safe cleanup.

ADR 0216 distinguishes a user-owned pre-acquired runtime package from that managed package. Exact revocation blocks import/staging, but the application cannot delete, move, quarantine or retain access to the external file; it cleans only proven app-created temporary inspection state.

Network loss, stale metadata, restart, reinstall, clock change, cached older catalog, mirror switch, offline package import or registry recovery cannot clear an accepted revocation. A stale state may delay accepting recovery but never resurrect known-revoked code. Catalog Delisting or ordinary end-of-support is not a security revocation and does not automatically disable an already installed verified runtime; a separate signed safety/security statement is required to stop it.

ADR 0205 prolonged refresh failure remains a passive in-app freshness notice rather than a new trust statement. It neither disables an installed verified and not-known-revoked runtime nor weakens any accepted revocation, and it never qualifies for an operating-system notification solely because the stale period grows.

AI Console and aggregate notifications expose response class, opaque affected identity/scope, reason category, issued/freshness state, waiting/contained/remediation status and safe action only. They never expose exploit details that would increase risk, raw package URLs/paths, credentials, asset names/content, subprocess output or private incident evidence. Diagnostics retain content-free state transitions and package/statement identities.

The current project has no Runtime Trust Statement schema/trust root, monotonic persisted runtime trust state, cross-job containment mapper, Waiting For Safe Runtime state or safe rollback/remediation resolver. Existing Runtime Package checksum verification and model/extension trust ADRs are useful patterns but do not implement runtime revocation. This ADR changes documentation only: it fetches no trust state/package, starts or terminates no runtime/model/job, reads no assets/results/private storage and changes no public IPC/schema/AI Worker API.
