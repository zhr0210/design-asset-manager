# Official Extension Catalog Uses Tiered Admission

Scope: Target architecture, refined by [ADR 0484](0484-extension-contracts-and-deferred-agent-development-access.md)
and the AI+ core boundary in [ADR 0483](0483-ai-plus-core-product-and-extension-boundaries.md).
The full ecosystem below is not a prerequisite for core product work; selected public
capabilities must satisfy their applicable contracts before third-party execution.
No SDK, catalog or sandbox is delivered merely by this decision.

The official Extension Catalog admits three visibly distinct publisher classes: First-Party Extension, Open-Source Community Extension, and Verified Proprietary Extension. Design Asset Manager's MIT license keeps the application, public Extension API, SDK, schemas, examples, and conformance tools open, but does not require every independently authored extension to adopt the same license or publish its source. All three classes use the same public API, permission consent, execution-cell isolation, platform confinement, update reapproval, failure-budget, and quarantine rules; first-party or paid status does not create ambient authority.

Every official entry identifies the publisher and signing key, package and version, artifact digest and size, license and cost/entitlement label, source-availability class, support and privacy links, declared data handling, permissions, platform/architecture, dependencies, Software Bill of Materials when executable dependencies exist, capability/confinement evidence, review scope and date, and current revocation state. Official Catalog Review applies only to the exact reviewed release and evidence set. It means the package passed the declared compatibility and safety gates; it is not a guarantee that the extension is defect-free, suitable for every asset, or authored by the project.

An Open-Source Community Extension provides a public source repository, a pinned source revision matching the submitted release, a declared open-source license, build and dependency instructions, and reproducible-build status. Reproducible output is preferred and displayed as evidence; when deterministic reproduction is not technically available, the catalog must state the limitation and retain independent package, dependency, protocol, permission, and platform checks. Merely publishing source without redistribution or modification rights is Source Available, not open source, and is reviewed under the proprietary class.

A Verified Proprietary Extension may remain closed source or commercial, but its entry must say so before installation. It requires verified publisher identity, per-release signing, artifact and dependency evidence, license/privacy/support disclosures, a vulnerability and revocation contact, and review material sufficient for its claimed capabilities. Proprietary extensions requesting staged originals, browser DOM/content, network access, native code, external workers, or other Sensitive Extension Permissions require enhanced review appropriate to the risk, which may include confidential source review, independent binary assessment, stronger provenance, and more frequent re-review. If maintainers cannot obtain sufficient evidence, the package cannot receive Official Catalog Review regardless of popularity or payment status.

Packages that do not meet official admission may be distributed through an explicitly user-added Catalog Trust Root under ADR 0153. The application labels the source and publisher, shows that official review is absent, preserves permission and confinement enforcement, and prevents third-party catalogs from imitating first-party or Official Catalog Review marks. A user-added trust root delegates signing and update identity only; it cannot override platform incompatibility, revoked grants, quarantine, or the official build's execution boundaries.

Extension API v1 does not provide in-app purchases, subscriptions, revenue sharing, payment collection, or a project-operated license server. A commercial extension may direct an explicit user action to the publisher's external purchase or authorization flow and declare any entitlement service host as Sensitive Extension Permission. The application does not collect publisher account passwords, payment details, or raw license credentials, and neither catalog metadata, application logs, other plugins, nor ordinary Namespaced Extension Storage may receive them. A durable secret or opaque entitlement broker requires a later separately reviewed capability; until then, commercial plugins must use an isolated, revocable external authorization design that does not treat ordinary plugin storage as a credential vault.

Every update repeats signature, artifact, manifest, ADR 0160 capability requirement/offer and bounded install-plan checks, ADR 0159 API/protocol/native-target compatibility, confinement, and applicable review checks. New official submissions cannot target only an end-of-support API major or directly depend on another plugin identity. Permission broadening still enters Permission Reapproval Required under ADR 0155, while native, dependency, data-handling, licensing, or ownership changes may require enhanced re-review even when the permission list is unchanged. ADR 0158 distinguishes Critical Security Revocation and Safety Suspension, which stop unsafe execution, from ordinary Catalog Delisting, which stops new official installs and updates without forcibly disabling a verified installed version. None silently deletes packages or user-authored plugin data.
