# Extension Revocation Is Risk Classified And Non Destructive

Scope: Target architecture, refined by [ADR 0484](0484-extension-contracts-and-deferred-agent-development-access.md)
and the AI+ core boundary in [ADR 0483](0483-ai-plus-core-product-and-extension-boundaries.md).
The full ecosystem below is not a prerequisite for core product work; selected public
capabilities must satisfy their applicable contracts before third-party execution.
No SDK, catalog or sandbox is delivered merely by this decision.

Extension catalog trust changes use three distinct responses. Critical Security Revocation covers confirmed malicious behavior, publisher-key compromise, capability escape, or another severe vulnerability requiring immediate containment. Safety Suspension covers credible data-corruption, privacy, compatibility, or dependency risk that makes further execution unsafe while investigation or repair continues. Catalog Delisting covers maintenance end, licensing or catalog-policy changes, publisher withdrawal, or another non-security removal that does not establish installed-code danger. These states are not interchangeable and the application shows the class, affected package/version or publisher scope, reason category, issued time, available recovery action, and source trust root.

A trust root distributes a signed, versioned Extension Trust Statement with a monotonic sequence, scoped publisher/package/version/artifact/key identifiers, response class, reason code, issuance and freshness metadata, and any signed remediation or superseding identity. The application verifies and persists the latest accepted sequence per trust root, rejects rollback to an older statement, and never clears a revocation merely because a statement or network response expires. Clearing or narrowing Critical Security Revocation or Safety Suspension requires a newer valid signed recovery statement under the catalog's documented key-recovery policy. Renderer-facing state remains path-free and excludes confidential review evidence.

Critical Security Revocation immediately blocks new activation, terminates every affected Extension Execution Cell, invalidates its grants and handles, cancels affected jobs with structured failures, and removes operation staging. The official build provides no continue-anyway control, including Developer Mode or a second catalog trust root for the same revoked artifact or compromised identity. The managed package remains non-executable until explicit uninstall or a verified remediation path; it is not silently deleted. Source forks remain free to change their own distribution policy, but do not inherit official trust claims.

Safety Suspension also stops execution and prevents automatic restart, but exposes only trusted host-owned recovery actions: inspect the reason, install a verified fixed update, perform Extension Recovery Export, disable, or uninstall. Export reads documented Namespaced Extension Storage through the host without loading plugin code and excludes cache, credentials, staged payloads, private paths, and unrelated application data. If plugin-specific conversion would require executing suspended code, the application exports a versioned raw structured container or reports that safe conversion is unavailable rather than running the plugin.

Catalog Delisting prevents new official-catalog installs and updates and removes the current Official Catalog Review mark, but it does not disable an already installed, verified version or revoke its existing user grants. Extension Library labels it Unsupported or Delisted, retains publisher/source/reason context, warns that fixes and compatibility updates are no longer supplied, and offers export, disable, uninstall, or an explicit future migration to another trusted catalog identity. Delisting cannot be represented as a security revocation merely to force removal, while later verified security evidence may escalate it.

Offline operation uses the Last Verified Extension Trust State. Loss of network does not turn trusted code into revoked code, clear an existing revocation, or downgrade a suspension. The UI shows trust-check freshness, and a stale state may block new installation, update, publisher-key migration, or removal of a suspension when fresh evidence is required, while an already active non-revoked version may continue under its existing permissions. Once a critical or safety statement has been accepted, restarting, reinstalling, changing clocks, using cached older catalog metadata, or going offline cannot bypass it.

No response class automatically deletes user assets, originals, previews, analysis results, provenance, user-authored plugin data, or the installed package. Prior analysis results remain attributed to the producing plugin and version and follow ADR 0143 lifecycle controls; they are not presented as freshly generated after execution stops. Uninstall and delete-data remain explicit separate actions. Trust checks and diagnostics store only package identities, statement metadata, state transitions, and content-free failure summaries, not user content or plugin payloads.
