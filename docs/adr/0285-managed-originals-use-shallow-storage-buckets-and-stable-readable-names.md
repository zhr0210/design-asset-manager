# Managed Originals Use Shallow Storage Buckets And Stable Readable Names

Original Asset Storage does not place a 100,000-asset library into one flat filesystem directory. New library-owned originals are allocated into application-managed, shallow **Managed Originals Storage Buckets** beneath the ADR 0282-bound Managed Originals Directory. Buckets bound per-directory entry count and keep Finder/File Explorer enumeration practical, but they are storage layout only: they never become Collection Groups, Asset Collections, Collection Memberships, Asset Sources, Source Tree nodes, or portable object identity, and their allocation labels do not imply user classification or provenance.

Every library-owned ordinary original member receives an **Original Storage Object Identity** before its final ADR 0280 commit. That identity remains stable when Candidate Promotion changes lifecycle ownership and does not depend on mutable content, source filename, physical path, Design Asset Identity, or an operating-system file identifier. A single-file Original Asset receives the application-created **Managed Original Storage Name**: a sanitized human-readable source-derived stem and actual validated extension plus ADR 0287's collision-checked Base32 disambiguator from its member storage identity. ADR 0340 instead groups declared members under a separate Compound Original Identity without merging their member identities, and ADR 0341 allocates one disambiguated Compound Original Directory while preserving capability-required names inside it. Complete identities remain authoritative; visible names are never sufficient by themselves to infer ownership, compound membership or correlate moved files.

Allocation validates the complete relative path under cross-platform reserved-name, character, length, case-folding, Unicode-normalization, regular-file, link, and boundary rules before staging. The original received filename remains metadata/provenance even when the safe physical stem differs. Two visually identical, byte-identical, same-named, case-equivalent, or normalization-equivalent originals never overwrite or share one ordinary file merely because their names or content match; content deduplication, if ever introduced, remains below the visible ownership contract and cannot merge Design Asset identities.

The bucket-allocation policy is versioned library state and affects new managed writes, copy-back recovery, and new-library restore allocation. ADR 0286 defines v1 as monotonic sequential buckets sealed after 2,000 committed allocation positions with no reuse or backfill; one single-file original or one Compound Original Directory consumes one position. ADR 0343 Compound Member Repair consumes no new position, while a complete Compound Directory Rebuild consumes one new permanent position and never releases the former one. Changing the policy does not move, rename, or rebalance already committed files. A future application-directed bulk reorganization is an ADR 0276 Material Library Migration governed by ADR 0003, while a safe user-performed move inside the bound directory remains ADR 0283 item-level path reconciliation. An externally accepted safe rename or move need not be forced back into the application naming pattern, and unknown files or directories appearing in a bucket are never auto-imported or treated as library-owned.

Full Library Backup identifies each original by portable object identity and digest rather than bucket or filename. New Library Restore may allocate the restored object under the destination library's compatible bucket policy without changing its restored logical identity, while merge and recovery continue to use explicit collision plans. Empty-bucket cleanup may remove only a proven application-created empty bucket under a separately bounded rule; it never deletes a non-empty, unproven, externally changed, or user-created directory.

ADR 0286 resolves the bucket allocation key and capacity, ADR 0287 resolves suffix encoding/default length, ADR 0288 resolves Unicode-preserving readable-stem transformation and dual length budgets, ADR 0289 resolves real-format-based extension selection, ADR 0290 resolves path-overflow behavior, ADR 0291 fixes the portable and platform path budgets, and ADR 0341 applies them to one compound directory plus its capability-required internal layout. The current implementation instead copies by source basename into one unbound flat singular `original` directory and may remove a source from the legacy library root; its separate download dry run uses case-insensitive append-counter names. It has no Original Storage Object Identity, portable owned-file inventory, collision-proof commit, bucket policy, or no-rebalance guarantee. This ADR records target architecture only and creates, enumerates, renames, moves, copies, or deletes no runtime/user file and changes no public IPC, database schema, or AI Worker API.

ADR 0385 deliberately does not reuse Managed Original Storage Name as the
default external Asset Export name. Original Asset Export derives a managed
copy's human-facing proposal from retained received-filename provenance and
truthful format evidence, so storage buckets, identity disambiguators and
library-internal paths do not leak into ordinary user-owned output.
