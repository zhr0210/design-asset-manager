# DateTime Custom Fields Preserve Declared Fractional Precision Up To Nanoseconds

DateTime metadata needs more precision than ordinary UI often shows, but preserving invented trailing digits would misstate source evidence. Every ADR 0436 Known-Instant or Unzoned DateTime therefore contains whole seconds, an exact 0–999,999,999 nanosecond component, and **Custom Field DateTime Fractional Precision** from zero through nine digits. The declared precision controls how many source-significant fractional digits are preserved and displayed; values such as `.1` and `.100` represent the same temporal point/components but retain different declared precision. Equality, ordering and ranges use the exact nanosecond value rather than the rendered digit count.

Ordinary editing displays seconds by default and never fabricates fractional digits. A minute-only manual, imported or migrated value is not yet a valid DateTime: the trusted host must visibly propose normalization to `:00`, and only explicit confirmation or a reviewed mapping rule commits that exact whole-second value with zero fractional digits. The application never supplies seconds merely because a parser or platform API defaults them.

A source with more than nine fractional digits enters **Custom Field DateTime Precision Conflict** rather than being silently shortened. Manual input remains invalid, AI output is not type-valid, and import/migration retains the source value until the user selects an explicit ADR 0424 rounding or truncation rule with representative before/after evidence. The same precision contract applies to original local components and the resolved UTC instant, so conversion between zones cannot add, drop or reinterpret fractional precision.
