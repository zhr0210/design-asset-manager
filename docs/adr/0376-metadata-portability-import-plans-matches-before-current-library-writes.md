# Metadata Portability Import Plans Matches Before Current-Library Writes

Every **Metadata Portability Import** targets exactly one currently active Registered Library and begins with side-effect-free **Metadata Portability Import Inspection**. Inspection decrypts an explicitly supplied encrypted envelope when required, validates the selected representation's declared version, schema and integrity, applies ADR 0372 package safety limits to `.dammeta`, inventories supported, unsupported and unavailable field/payload classes, and reports blocking issues before any library write. Under ADR 0382, native schemas, user field mappings and extension adapters must first normalize into one host-validated Metadata Import Draft; successfully inspecting a file or draft neither accepts its values nor proves that its records belong to assets in the target library.

Inspection produces a **Metadata Import Mapping Plan** bound to the target Portable Library Lineage Identity, Local Library Instance Identity and a consistent target-library evidence generation. A record may receive an automatic proposed target only when one deterministic route resolves to exactly one current Design Asset: the same portable lineage plus Design Asset identity, or complete ADR 0374 Original Content Match Evidence matching the asset's current verified single-file or Compound Original evidence. When both routes exist they must agree; contradictory identity/content evidence is a blocking mapping conflict. Multiple logical assets may legitimately share exact bytes, so a content match with two or more targets remains ambiguous rather than choosing one by rank or creation time.

Every automatic result is a proposal shown in review, never write authority. Filename, former/current path, display title, timestamp, byte length alone, source URL, Portability Review Thumbnail pixels, perceptual similarity, Duplicate Signals or one Compound Original member cannot automatically map a record. They may support human review where separately allowed, but they do not turn uncertainty into an exact match.

Unmatched and ambiguous records remain **Pending Metadata Mapping** entries with their reason and compatible candidate choices. The user may map one to an existing Design Asset, exclude it, or first add/reconnect an Original Asset through the normal ownership/reference workflow and then refresh the plan. Metadata records, Portable Asset Identity and Portability Review Thumbnails never create a placeholder, metadata-only Design Asset, Candidate, Original Asset, Required Preview or ownership relationship.

No mapping writes metadata until the user reviews the plan and explicitly confirms its selected mappings. If the active library, its instance identity or relevant target evidence changes before confirmation, affected proposals become stale and require refresh; the operation never follows a library switch or writes across multiple libraries. Applying the same source to another library requires a separate inspection, mapping plan and confirmation. ADR 0377 resolves field/result conflicts by semantic type and provenance without silent scalar overwrite, destructive set replacement or manual-value displacement; ADR 0378 governs item-atomic execution and undo, while ADR 0379 makes unresolved persistence an explicit portable source-detached choice.

The current application has no Metadata Portability Import Inspection, Metadata Import Mapping Plan or Pending Metadata Mapping workflow. This ADR records target architecture only and decrypts, reads or inspects no actual user package, matches or creates no asset, and selects, imports, analyzes, stages, writes, rewrites, converts, moves, deletes or changes no runtime/user file, credential, sidecar, directory, database, cache, backup, metadata value, analysis result or source relationship and changes no public IPC, database schema or AI Worker API.
