# Trust Notification Preferences Are Independent And Device Local

App Settings exposes two independent device-local operating-system delivery preferences: **AI Execution Security Notifications** and **Model Result Advisory Notifications**. Both default On after operating-system notification permission is available. The first covers newly verified model/runtime execution revocation or suspension; the second covers materially new/reopened ADR 0193 Model Result Advisories. Neither setting controls catalog refresh, signature verification, trust persistence, execution containment, in-app attention, result behavior or remediation.

Turning off AI Execution Security Notifications suppresses only its future OS notification projection. Critical ADR 0165/0192 execution blocks, job containment, Waiting For Safe Runtime and AI Console status still apply immediately with no continue-anyway behavior. Turning off Model Result Advisory Notifications suppresses only future advisory OS summaries; Model Library, Result Provenance Advisory, Has Model Result Advisory filtering and ADR 0195 acknowledgement/reopening remain unchanged.

ADR 0175 Long-Running AI Operation Notifications remains a third separate setting. Disabling one class never disables the others, and there is no ambiguous global “all AI notifications” toggle that also changes analysis behavior. Operating-system permission, per-app notification controls, Focus/Do Not Disturb, lock-screen policy and platform delivery always take precedence; the application never attempts to bypass them.

ADR 0199 coalescing considers only notification-eligible transitions whose class is enabled at emission time. For mixed attention, disabling advisory delivery may yield an execution-only summary and ADR 0200 routes its opaque notification scope accordingly; all disabled-class detail remains available in the in-app AI Trust And Advisory Summary. If every eligible class is disabled or OS delivery is unavailable, no system notification is emitted and no attention is lost.

Changing a preference is prospective. Re-enabling does not replay previously suppressed, already pending or acknowledged transitions; only a later materially new transition is eligible. Disabling does not mark an emitted/pending advisory acknowledged, dismiss an OS notification already owned by the platform, clear deduplication evidence or alter resolved history. Resetting settings to defaults likewise does not generate synthetic notifications.

These preferences are application-installation/device state, not library state. They do not enter ADR 0185 Full Library Backup, asset export, library merge or Portable Library Lineage Identity and do not roam merely because a library is restored on another device. Each installation follows its own OS permission and user preference. Public state exposes only boolean preference/permission availability and safe reason codes, never device identity, notification history payloads or library content.

ADR 0202 keeps permission Not Requested at first launch and requests it only after a contextual user action/primer, never from an automatic event. The current project has no Electron system-notification permission model or these three independent settings; generic settings and renderer toast state do not implement them. This ADR changes documentation only: it requests no permission, sends no notification, reads no OS/private/library state and changes no public IPC/schema/AI Worker API.
