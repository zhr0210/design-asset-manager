# DateTime Custom Fields Separate Known Instants From Unzoned Local Times

Asset metadata often contains a useful local date and time without enough evidence to identify one moment, so every DateTime Custom Field Value has one of two explicit states. A **Known-Instant Custom Field DateTime** preserves its entered local calendar/clock components, explicit UTC offset, resolved UTC instant and optional portable IANA time-zone identifier. An **Unzoned Custom Field DateTime** preserves only its local calendar/clock components and explicitly has no offset or instant. Missing zone evidence from EXIF, legacy metadata, manual input, AI or import never inherits the current device zone, operating-system locale or another asset's zone.

Known-Instant values compare, sort and filter by their resolved UTC instant; their stored original local components and offset remain authoritative evidence, so device-zone or time-zone-database changes never rewrite the value. A converted display in another zone is presentation only. Unzoned values compare and range-filter only by their local components. Query surfaces expose the state and require an explicit instant or local-calendar comparison mode; they never mix Unzoned values into one absolute timeline, although users may filter specifically for zone-known or zone-unknown values.

**Assign Time Zone To Custom Field DateTime** is an explicit value edit, import mapping or ADR 0424 rule-governed conversion that resolves an Unzoned value using a declared UTC offset or IANA zone. If IANA rules map the local time to no instant during a daylight-saving gap, assignment is invalid until the local time or rule changes; if they map it to two instants during an overlap, the user or declared import rule must choose the exact offset. The host never picks the earlier/later occurrence or shifts a gap automatically. Date remains a zone-free calendar value. ADR 0437 owns whole-second and fractional precision without changing these state or zone semantics; ADR 0438 owns preservation and revalidation when a later DateTime validation rule becomes restrictive.
