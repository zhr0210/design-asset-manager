# Extension API Has A Declared Compatibility Window

Scope: Target architecture, refined by [ADR 0484](0484-extension-contracts-and-deferred-agent-development-access.md)
and the AI+ core boundary in [ADR 0483](0483-ai-plus-core-product-and-extension-boundaries.md).
The full ecosystem below is not a prerequisite for core product work; selected public
capabilities must satisfy their applicable contracts before third-party execution.
No SDK, catalog or sandbox is delivered merely by this decision.

Extension API uses its own semantic version independent from the Design Asset Manager application version. A major version may contain documented breaking contract changes; a minor version adds backward-compatible optional capabilities or fields; a patch version corrects behavior without changing valid public meaning. Internal module, Electron, database, renderer, or build-tool versions do not become Extension API versions. Breaking behavior never ships silently in a minor or patch release merely because the internal implementation changed.

Before the first stable SDK, ADR 0484 requires an explicit published support and migration policy, while experimental contracts remain labelled unstable. The former current-plus-previous-major and no-less-than-twelve-month schedule is a candidate for that release decision, not an already validated service commitment. Any support promise actually published to external users remains binding and is not silently shortened by this clarification. The published Extension API Compatibility Window identifies stable, supported, deprecated, end-of-support and security-suspended versions plus the earliest removal date. A severe security issue may suspend an unsafe path under ADR 0158, with an explicit reason and migration or remediation path rather than pretending the compatibility promise never existed.

Each extension manifest declares a bounded Declared Extension API Range. Extension Host selects the highest mutually supported stable version before loading any plugin code and records the Negotiated Extension API Version in activation evidence. No overlap means Incompatible API and no execution; the host does not guess, coerce an unbounded wildcard, expose private IPC as fallback, or silently reinterpret a newer contract as an older one. Optional capability negotiation remains explicit, so support for an API major does not imply every newer minor capability or platform feature is available.

Deprecation metadata names the affected schema, operation, field, error, permission, UI slot, or protocol behavior; its replacement; first deprecated version; earliest removal date; and migration guide. The public repository maintains versioned schemas, SDK types, examples, fixtures, conformance tests, changelog, and bounded compatibility adapters for every supported major. An adapter is public, deterministic, tested, time-bounded, and included in the compatibility matrix; heuristic shims and internal-interface imports are not compatibility support.

Application and extension updates run Extension Compatibility Preflight without executing plugin code. It compares installed manifests, supported API ranges, ADR 0160 capability requirements/offers/bindings, trust state, platform/architecture, confinement evidence, worker protocol, and any native target. Before an application upgrade, Extension Library lists plugins that remain compatible, need an available plugin or capability-provider update, will become incompatible or Dependency Unsatisfied, or cannot yet be proven compatible. The user may still upgrade the application, but plugins without a valid negotiated target are disabled before execution and retain their package, permissions, Namespaced Extension Storage, prior results, and provenance. A later compatible plugin or capability-provider update may reactivate them after normal verification, permission-diff review, binding selection, and transactional storage migration.

Portable worker and RPC protocols are language-neutral and version-negotiated separately from the application. Native extensions additionally declare a Native Extension Target covering operating-system family and minimum version, CPU architecture, package/runtime ABI, entrypoint identity, and required confinement adapter. A matching Extension API range cannot override a native target mismatch. Catalogs publish separate native artifacts and conformance evidence where targets differ; one successful macOS or Windows artifact never establishes compatibility for the other platform or architecture.

Catalog admission and every package update verify the declared range against currently supported and announced compatibility windows. New official submissions cannot target only an already end-of-support major. Before ending support, maintainers publish migration guidance, update conformance fixtures, surface developer warnings, and keep the old-major test lane through its promised date. Installed incompatibility is a lifecycle state, not data deletion, security revocation, or license failure, and the UI reports the exact missing API, protocol, capability, platform, architecture, or ABI evidence.
