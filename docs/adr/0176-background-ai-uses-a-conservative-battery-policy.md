# Background AI Uses A Conservative Battery Policy

ADR 0173 Local AI Resource Governor applies a cross-platform Background AI Power Policy with explicit evidence states: External Power, Battery Normal, Operating-System Low Power Mode, Low Battery, Thermal Pressure and Unknown. Platform adapters report availability, freshness and severity rather than inventing a battery percentage, thermal level or healthy state. Unknown or stale power evidence uses the conservative policy applicable to the current known source and never increases concurrency.

On external power, eligible background work follows the normal resource policy. On Battery Normal, the default policy is **Light Baseline Only**: only ADR 0169 newly changed asset baseline work whose exact artifact/runtime execution envelope is classified Light and whose combined resource/energy evidence fits may start. Heavy automatic analysis, confirmed historical Backfill, Idle Extended Analysis, background calibration and other extended work remain Waiting for Power. “Light” comes from verified artifact/runtime/calibration evidence and the current recipe, not model file size, parameter count or a hard-coded model name.

The independent **Allow Heavy And Extended Background AI On Battery** setting is Off by default. Turning it on permits those background classes to enter ordinary ADR 0173 admission on Battery Normal; it does not guarantee execution, override memory/thermal/foreground limits, enable no-window analysis, prevent sleep, launch at login, install a model or authorize external AI. The setting is named and explained as a battery-cost override rather than the ambiguous “allow background AI,” because Light Baseline Only remains the default battery behavior.

Operating-System Low Power Mode, Low Battery or actionable Thermal Pressure pauses all new background AI regardless of that override. An in-flight unit yields and commits only at the same atomic boundary defined by ADR 0173; critical pressure may use bounded cancellation and discard incomplete output. Models without an active foreground need lose idle residency promptly. The application never uses a power-save blocker to keep the machine awake for automatic analysis, backfill, installation or calibration, and sleep/wake behavior remains governed by ADR 0174.

An explicit foreground user analysis may run on battery after showing a non-modal power-state/resource badge and current estimate when evidence exists. It remains subject to hard memory, accelerator, trust and critical thermal gates. Low Power Mode or Low Battery is a warning for a bounded foreground action, while critical thermal/memory pressure may block it; the user cannot click through a device-safety gate. User-initiated installation/download may proceed under its own network/storage policy, but any heavy post-install calibration waits or requires the same visible foreground admission rather than starting silently.

When external power returns or Low Power/Thermal state clears, the governor refreshes resource evidence before ADR 0168 Pending Intent Reconciliation. It does not immediately launch every deferred job: priority, foreground state, residency, storage and current resource gates still apply. Repeated power transitions debounce to avoid load/unload thrash. Queue and tray/UI states distinguish Waiting for External Power, Waiting for Low Power Mode to End and Waiting for Thermal Recovery without exposing device serials or private process details.

Power thresholds and platform mappings are versioned policy, not scattered magic numbers. Where the operating system exposes only coarse events, the UI reports that coarse evidence and does not claim an exact percentage or temperature. The same shared state shape is used on macOS and Windows while adapters preserve real platform differences. Users may inspect the current power reason and restore default policy without resetting other automatic-analysis settings.

The current project has no Electron power-monitor integration, shared power-evidence state, verified Light execution classification, battery-specific queue admission, low-power/thermal waiting reasons, battery override or resume debounce. Existing generic settings, GPU monitoring and model keep-alive do not prove these semantics. This ADR records the target policy without querying battery/thermal state, starting a worker, changing public contracts or reading runtime/task/user data.
