# Model Library Installs Data Only Pinned Artifacts

Model Library installs Model Artifact Packages containing weights and allowlisted declarative model data, not executable repository code. Each catalog entry points to a signed Model Artifact Manifest with model/checkpoint identity, publisher and source repository, immutable revision, exact relative file list, role, media/container type, byte size and cryptographic digest, license/acknowledgement, architecture, quantization, tokenizer/preprocessor identity, capability, runtime/backend requirements, model-space identity where relevant, and platform/resource guidance. Repository presence, a model name, filename extension, mutable branch, tag, or successful download does not establish package identity.

Allowed weight containers initially include structurally validated safetensors, GGUF, and ONNX with explicitly listed external tensor data. Allowlisted supporting roles may include bounded JSON configuration, tokenizer or SentencePiece data, vocabularies, merges, templates, label maps, and equivalent non-executable resources required by a declared runtime. Format and role validators enforce structure, dimensions/metadata, paths, counts, lengths and resource limits; an allowed extension alone is insufficient. Python pickle-based weights or checkpoints, arbitrary serialized objects, and undeclared archives are rejected rather than deserialized to discover whether they are safe.

A Model Artifact Package cannot contain or activate Python, JavaScript, WebAssembly, shell scripts, dynamic libraries, executables, package-manager metadata that triggers install hooks, or another runtime payload. Model installation and inference prohibit `trust_remote_code`, arbitrary module import, repository install scripts, automatic dependency installation, and runtime fetch of missing files. Approved loaders use local verified files only and do not execute model-supplied code. A model requiring custom architecture, tokenizer, preprocessing, postprocessing, operator, or runtime code declares an ADR 0160 capability requirement satisfied by a separately packaged and reviewed Model Runtime Capability Pack under ADR 0151 through ADR 0160. Installing weights never grants trust to that code pack, and installing the code pack never downloads weights without a separate Model Library action.

Hugging Face or another external object store may transport catalog artifacts, but the source is pinned to an immutable commit or equivalently signed release identity plus the exact manifest file set and digests. The installer does not perform an unrestricted repository snapshot, follow a moving `main` or latest tag, accept newly appearing files, or infer an executable allowlist from repository contents. Mirrors may serve only byte-identical declared artifacts. ADR 0163 keeps gated authentication in a dedicated operating-system-backed vault and issues only bounded download leases; raw tokens, headers, URLs, repository credentials and local paths never enter renderer/worker/plugin responses, process arguments, ambient environments or logs.

Download uses managed partial storage and promotes only after every expected file, size, digest, role, structural validator, license and runtime compatibility check passes. Unexpected, missing, duplicate, case-colliding, symlinked, path-escaping or executable files fail verification. ADR 0162 stores verified bytes in an immutable content-addressed Model Blob Store and represents a package/variant through manifest references, allowing identical files to deduplicate without merging identity or licensing. Runtime-generated compilation, quantization, conversion, repaired configuration, tokenizer cache or backend-specific optimization belongs in a separately keyed Model Derived Runtime Cache with source-manifest and toolchain provenance; loaders never rewrite the verified package in place. ADR 0164 updates install as new side-by-side artifact identities until verification and explicit selection complete, preserving the active artifact on any failure.

The official Model Catalog and explicitly added third-party model catalogs use separate Model Catalog Trust Roots, signed metadata and ADR 0165 monotonic Model Trust Statements plus publisher/source identity and compatibility evidence. A third-party catalog is visibly non-official and cannot weaken data-only formats, immutable revision, exact file/digest, no-remote-code, no-pickle, license, runtime compatibility, readiness-probe or known critical-digest blocking requirements in the official build. An arbitrary repository URL is not a trusted one-click Model Library entry. ADR 0166 permits explicit local import through the same data-only validators and managed storage without treating a local folder or successful probe as catalog trust. Forks may choose other policies without inheriting official model safety or compatibility claims.

Readiness probes run only after artifact verification, use the declared built-in runtime or verified capability binding, remain local and bounded, and do not read user assets or contact the model repository. Active Capability Model and analysis provenance record Model Artifact Manifest identity, runtime/capability provider, recipe and backend evidence. Removing, updating, revoking or replacing an artifact follows ADR 0143 through ADR 0145 and does not silently reanalyze assets, merge embedding spaces, delete prior results, or authorize external upload.
