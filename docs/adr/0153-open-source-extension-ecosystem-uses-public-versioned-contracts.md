# Open Source Extension Ecosystem Uses Public Versioned Contracts

Scope: Target architecture, refined by [ADR 0484](0484-extension-contracts-and-deferred-agent-development-access.md)
and the AI+ core boundary in [ADR 0483](0483-ai-plus-core-product-and-extension-boundaries.md).
The full ecosystem below is not a prerequisite for core product work; selected public
capabilities must satisfy their applicable contracts before third-party execution.
No SDK, catalog or sandbox is delivered merely by this decision.

Design Asset Manager is an MIT-licensed open-source project. Extension safety policy in the official build does not prohibit third parties from reading, modifying, forking, rebuilding, redistributing, or replacing project code and catalogs under the repository license. Fork maintainers may choose different trust roots or product policies, but they cannot inherit official publisher identity or compatibility claims without their own signing and release evidence. Source-code freedom and official-binary plugin trust are separate concerns.

The target developer kit publishes a versioned Extension API independent from internal module layout and application version. The public surface includes manifest JSON schemas, capability requirement/offer/binding vocabulary under ADR 0160, tiered permissions and reapproval semantics under ADR 0155, a TypeScript Extension SDK for commands and declared UI slots, a language-neutral worker protocol for Format Capability Packs and compute workers, ADR 0382 Metadata Import Draft/Adapter schemas, path-free RPC message schemas, lifecycle/state contracts, error codes, example packages, and protocol fixtures. Retired website plugin types are not a public SDK. Internal interfaces such as the Runtime Package package-id dependency resolver remain implementation details until adapted behind this public boundary; third-party packages do not import `src/main`, Electron objects, SQLite services, React stores, private IPC names, or another plugin.

An isolated Extension Host brokers every official-build plugin call but never executes third-party code itself. Under ADR 0156, each plugin identity receives a separate Extension Execution Cell, Inspector UI uses an isolated sandboxed surface, and native or portable workers use platform-constrained processes with failure budgets and quarantine. Capability negotiation matches plugin API range, requested features, package kind, platform/architecture, confinement evidence and optional native ABI before activation. Unsupported optional operations fail through declared capability evidence rather than crashing the host. Worker extensions exchange structured messages plus bounded staged files or approved binary transport rather than base64 payloads or direct filesystem access.

The target repository provides Extension Developer Mode for explicit local development. It can load an unpacked or locally built unsigned package, show a persistent developer/untrusted state, expose validation and structured logs, support reload, and keep the same declared permissions and process isolation wherever technically possible. Developer Mode never becomes an automatic production trust bypass. A scaffolding CLI or template, manifest validator, local Extension Host harness, sample Feature Plugin, sample Format Capability Pack, macOS/Windows conformance tests, and packaging/signing guidance form the minimum supported developer kit.

ADR 0159 gives Extension API independent semantic versions and a declared compatibility window. Under ADR 0484, the former current-plus-previous/twelve-month schedule is a candidate to confirm before the first stable SDK, not an existing publication promise or a prerequisite for an experimental contract. The official build negotiates a bounded manifest range before execution, provides only documented tested adapters for supported versions, and displays the exact missing or deprecated contract. Catalog CI runs versioned manifest, permission, package safety, RPC/worker protocol, platform/architecture/native-target, confinement, crash-safety and declared capability fixtures. Native packs publish separate artifacts per supported target, while language-neutral workers may share source or portable artifacts when their runtime and confinement evidence pass.

The official catalog may contain First-Party, Open-Source Community, and Verified Proprietary Extensions under the tiered admission and disclosure policy in ADR 0157. Community and commercial publishers retain their identity, license, source-availability class and support responsibility and sign their releases; catalog inclusion is version-specific compatibility and review evidence, not transfer of authorship or a guarantee against every defect. Contributors may propose catalog metadata and packages through the open repository review process. Users may explicitly add a third-party catalog trust root under ADR 0151, with its own publisher key, permissions, signed Extension Trust Statements, revocation and update responsibility. ADR 0158 prevents a second trust root or offline cache from overriding a critical statement for the same official-build artifact or compromised identity; arbitrary package URLs never acquire execution trust merely because the project is open source.

Public schemas, SDK and protocol documentation remain usable by independent catalogs and forks without requiring a proprietary service. ADR 0154 defines the initial scoped contribution surfaces rather than exposing project internals wholesale. Compatibility bugs and API proposals use the normal open issue and contribution workflow. Breaking public Extension API changes require an explicit major-version transition, ADR 0159 support window, migration guidance, conformance updates and release notes rather than silently following internal refactors.
