# Dropover 式交互允许平台原生实现

用户在 Dropover 逆向研究后的设计访谈中接受：DAM 的相关功能可以采用必要的原生模块，并按 macOS、Windows 分别实现和验收，不要求全部功能只通过 Electron 标准 API 完成。现有工作窗口的交互品质是后续设计要解决的问题；采用原生组件本身不构成流畅性或行为等价的验收证据。

Electron、React 与 Local DAM Host 继续作为当前应用基础；原生交互适配可以访问必要的系统窗口、输入及拖放机制。Host 保留资料库、工作集、任务、文件交接和提交权威，新的窗口实现不得形成第二套业务数据库或绕过成员、修订、会话撤权及取消保护。现有工作集语义遵循 ADR 0489，双客户端共用 Host 遵循 ADR 0491。

相比只用 Electron 标准窗口接口，这个选择允许更深的平台交互控制，同时接受分别构建、打包、维护和真实验收的成本。它不承诺消除 Electron 的全部运行成本，也不承诺 Windows 与 macOS 系统场景一一等价。

本决定仅确认原生实现的前提。是否由原生层直接拥有架子拖动、收缩、停靠和动画，哪些内容仍由 React 绘制，以及暂存内容与已入库工作集的关系，仍待逐项确认；没有授权把访谈中未定方案写成已实施架构或移除既有功能。

参考：[本机 Dropover 逆向报告](../../artifacts/reverse-engineering/dropover-5.2.0/REPORT.md)、[工作窗口当前适配](../../src/main/work-mode/electron-work-window.ts)、[工作集与窗口权威](0489-work-sets-separate-saved-references-from-native-window-authority.md)、[共享 Host](0491-local-clients-share-one-host-and-product-workspace.md)。

## 2026-10-13：已确认的性能与视觉取舍

用户选择以悬浮工作窗口的响应与动画达到原生级为性能目标，并允许在适合的UI/UX中直接采用原生组件；macOS前端应尽量与系统组件保持一致的视觉语言。此选择接受原生呈现与共享工作台分别维护的成本，保留既有Electron/React/Host业务基础。整体资源开销仍需独立测量与优化，本决定没有设定与Dropover相同的整应用资源预算。

macOS视觉方向优先使用合适的系统控件、材质、字体、层级和交互状态；仍由React呈现的界面遵循一致的视觉语义。当前素材内容布局及Host权限/提交权威保持。采用原生组件不自动证明响应、动画或视觉资格；须在实际应用与设备上验证。

用户随后接受：系统外观与Dropover自定义视觉细节冲突时，以macOS系统视觉优先；Dropover作为拖动、吸附和动画行为的参照，素材展示保留DAM的信息结构。这不要求复制Dropover的自定义按钮或逐像素界面。

用户进一步接受的呈现边界：整个悬浮工作窗的紧凑态、展开态、菜单、输入和系统拖放由AppKit负责；独立大预览与主工作台继续使用React，遵循一致的macOS视觉语言。数据提交、成员授权及文件交付仍由Host持有。

色板明确改为“添加”按钮打开参考图风格的原生颜色选择浮层，替代展开窗右侧直接HEX输入；选择器仅包含颜色区域、色相条与HEX显示，保存不透明六位HEX颜色。确认才加入工作色板，取消不提交。

可量化性能门槛及原生进程合并策略仍待访谈确认。本次决策不表示整个原生UI已完成验收，也不授权全应用重写。
