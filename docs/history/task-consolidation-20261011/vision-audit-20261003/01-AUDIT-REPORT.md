## 1. 结论先行

**项目没有在产品定义上偏离“本地优先、AI 为核心、面向视觉创作的素材工作台”。真正需要调整的是交付重心与基线治理。**

已有工作具有真实价值：单一 Host 权威、受控素材收录、引用式组织与工作集、AI 结果和人工修改分离、原生与浏览器共用 UI、取消/迟到结果/未知提交保护、统一 AI 导航，都在当前代码和明确的实施记录中留下了可追溯的结构。[S01–S08, S16–S23]

但三个落差仍明显：

1. **“Windows 界面能运行”与“Windows 正式 AI 可以使用”不是同一状态。**正式视觉预处理仍限定 macOS arm64；受管 schema 升级的备份资格仍限定验证过的 Mac/APFS/SQLite/native 组合；HEAD 的 Pi 清单也是 Mac 版本。[S22–S24, E01]
2. **“基础设施已经很完整”与“默认基础分析真的产出结果”不是同一状态。**B01 仍收集计划，生产 OCR 资格仍为空；独立描述、三能力后台执行和完整资源 Governor 仍未闭环。[S20, S25–S27]
3. **“报告认真保留了证据”与“接手者能复现当前交付”不是同一状态。**当前提交、未提交改动、冻结候选、旧 generated build identity、历史 README 和 `.scratch` 本机证据同时存在，需要统一入口，而非继续叠加新的总报告。[S08–S14, S31–S37, E01–E03]

建议：**保留架构骨干，立即收敛当前 Windows 基线和错误隔离；双客户端停止无边界扩展；随后回到“可用的真实 AI → 独立描述 → 资源预算 → 后台三能力”的原路线。**不要重写整个应用，也不要把更多治理模块当作产品进展。

## 3. 原愿景与最新批准的边界

### 3.1 仍应坚持的原目标

本地优先；基础素材能力不依赖模型；标签、描述、OCR 为基础分析能力；反推主动触发；AI 结果可追溯、可检索、可修订；人工内容优先；模型和 Runtime 可替换；资源占用能按用户偏好调节；工作集/原生参考窗口服务设计过程；macOS/Windows 为当前目标，手机为后续收集管理入口。[S01–S05, B01]

### 3.2 双客户端不是未经授权的“跑偏”

ADR 0491 与双客户端规格明确记录用户后续确认：Desktop 与本机 Browser 共用正式 React 产品和同一个 Electron Host；Browser 可日常使用并供可见交互验收；本地页面文件选择由 Host 校验；关闭客户端与退出整个 DAM 分开。[S06–S07]

该选择没有把产品变为云 SaaS，没有重新引入被退休的网页采集，也没有让浏览器直接写 SQLite 或启动任意进程。从当前 Main、共享 Client、HTTP 适配器可见，这个边界正在被落实。[S19–S21]

**需要控制的是新增能力的范围和成本，不是撤销已经确认的双客户端。**不得以“只为 AI 测试造了一个浏览器”为由擅自删除用户已认可的正式客户端；也不得用本机 Browser 通过替代原生窗口/跨屏/安装验收。

### 3.3 不应恢复旧验收规则的绝对化解释

2026-10-02 的 AGENTS 与 UI/UX 流程允许浏览器工具定位可见控件后真实点击/键入；禁止业务注入、改 hash、IPC/API 代办步骤。这个较新范围优先于旧计划中更严格的工具表述。[S01, S15]

因此，报告不会把“使用可见控件定位”本身判为违规。真正需要审查的是：是否从普通入口开始、是否操作正式客户端、是否绑定合成 profile 与构建、是否重读持久结果，以及是否把后台测试冒称 Computer Use。

## 4. 已经做对且应保留的部分

### 4.1 导航与 AI 页面确实在简化

旧 `AiConsolePage.tsx` 已成为两行兼容导出，真实页面为 `AiWorkspace.tsx`。AI 工作区按连接、任务模型、本地模型/OCR、后台资源、诊断分区；旧 URL 和设置参数通过统一 alias 转向 canonical route。诊断中的工程验收入口也被收纳，而非占据整个普通配置页面。[S16–S18]

这不证明当前每个尺寸和状态都已通过 UX，但能确认之前“新面板继续堆在 2,583 行旧控制台上”的结构已经改善。两行兼容壳可以保留，不必为了删文件把旧链接打断。

### 4.2 一个 Host、两种传输，未观察到第二套业务数据库服务

Main 只注册一份命令 handler。Desktop 经 IPC，Browser 经 loopback HTTP，进入共同的权限、切库、receipt 与 Controller 逻辑；浏览器身份不伪装为 Electron sender。原生 Asset Card/Work Window 有额外角色范围。[S19–S21]

HTTP 层检查 Host、Origin、会话与 CSRF，命令必须已登记，媒体不是任意路径服务器。已有重发准入会在产生业务效果前登记当前文档调用序号。本次独立重放了这部分重复请求保护。[E03]

这是方向正确的结构，不等于本次完成了完整网络安全审计。后续应围绕具体权限与错误结果补测试，而非重建微服务。

### 4.3 冲突、草稿和未知提交的区分有产品价值

双客户端不能静默互相覆盖。当前规格/模块将正式保存、Host 已接收草稿、未送达输入、未知提交与可恢复记录分开；退出和切库会检查多个客户端。已有实施矩阵还保留了失败后修复的记录。[S07–S08, S20–S21]

这些代码不是因为“行数多”就应删除。可优化其所有者和接口，但要保留精确重读、显式采用新基准、旧 writer 撤权、取消后输入不丢等可观察行为。

### 4.4 安全准入没有被当成模型可用证明

当前矩阵明确限制不完整 Provider 路径；生产后台 OCR 资格仍为空。实现说明保留真实账号、真实模型、Windows 安装与原生系统验收缺口。这比把目录、fixture 或按钮可用当成生产通过更诚实。[S08, S25–S27]

问题是这些缺口必须进入有终点的交付任务，不能长期以“安全拒绝”取代最初承诺的功能。

## 5. 重点发现与调整建议

### F01｜Windows 资格拒绝扩大为共享准入长期暂停

**优先级：P1。证据：源码 + 本次独立生产模块反例。**

`visual-preparation.ts:8–10` 对非 `darwin/arm64` 在任何图片解码前拒绝。`visual-admission.ts` 把 `VISUAL_CODEC_UNQUALIFIED` 和实际估算超限一起设置为全局 `estimateFailed=true`；`resume()` 不会解除它。OCR 与 Pi 生成图探测也复用该准入器。[S22–S23]

本次在 Windows 调用原生产准入器，结果为：

```text
初始 accepting=true，资源计数全部 0
→ prepare：VISUAL_CODEC_UNQUALIFIED
→ 所有占用归零，但 accepting=false
→ resume 之后仍为 false
→ reserveOcr：VISUAL_ADMISSION_SUSPENDED
→ reservePiProbe：VISUAL_ADMISSION_SUSPENDED
```

使用一个合成字节，被平台检查提前拒绝；无 Worker、HTTP、模型、资料库或真实凭据。它证明原生产函数的失败传播，**未在完整 GUI 中重放用户操作**。Main 的共享实例接线说明该传播有正式调用基础。[S20:543–585, E04]

**建议：**区分“能力/平台不支持”“任务失败”“实际资源危险/未确认退出”。仅不支持的视觉能力保持不可用，不应锁死互不相关的 OCR 与探测；实际峰值超限/UNKNOWN 仍按原资源池风险保护。补当前反例以及 genuine unsafe/late release/cancel/drain 的正反向测试，不能简单删除资格或无条件重置 `estimateFailed`。

### F02｜Windows AI 的两道资格尚未闭环

**优先级：P1（对 Windows AI 交付）。证据：直接源码。**

第一道是视觉预处理；它并不会因为选了云端 API 就消失，正式素材调用仍要先生成受控图像。[S20, S22]

第二道是 `tag-intent-backup.ts:48–60`：升级前备份仅接受指定 Mac/APFS、SQLite version/source 和 native artifact SHA。`host-schema-maintenance.internal.ts` 虽集中复用了维护过程，却没有扩展资格。Windows 新库创建成功，不等于独立标签或后台意图的后续 schema 升级成功。[S24, S30]

**建议：**把“Windows 素材基本操作”“Windows 图片预处理”“Windows 已有 v9–v13 升级路径”“Windows 真实模型/Provider”列成四个独立状态。先支持一个明确的本地 NTFS/锁/原生依赖组合，以临时真实数据库做备份、验证、回滚、磁盘不足、句柄和中断测试。禁止删除 OS/hash 检查来把不可用变成未经证明的可用；不预设新 schema 号。

### F04｜当前代码索引门未通过，不能沿用历史全绿

**优先级：P2。证据：本次独立命令。**

`context:check` 当前报告 693/693 已跟踪源归属，却因三个 `platform-ai-branch-*` 测试入口处于未跟踪状态而失败，并提示两个未跟踪一方源码不在信任覆盖内。[E02]

这里不是“文件真的都不存在”，也不是类型检查失败。它是当前命令表和可交付跟踪集合不一致。以标准化方式记录此区别，比简单删检查、加白名单或顺手全暂存更重要。

**建议：**分别处理已批准的 schema 维护提取、保留的旧 Runtime 提取和 Pi 平台准备。每组形成可评审的变化/测试闭包；准备进入候选的文件必须确实随候选交付。归属检查针对最终候选重跑，历史 693/693 不自动变成本次 PASS。

### F05｜“当前状态”入口分裂，部分会把后续 AI 导回旧方向

**优先级：P2。证据：文档直接矛盾。**

- `README.md` 仍说当前只有单 Asset Card，并把 DESIGN 指向 mobbin；实际已有工作集/共享 UI，根 AGENTS 的 DESIGN 才是活跃来源。[S01, S10, S16–S20]
- `docs/handoff/CURRENT-STATE.md` 仍引导旧的跨机 RUX 状态，没有容纳 10 月 3 日的局部 Browser CU 和选择性提交范围。[S11]
- `RELEASE-ACCEPTANCE.md` 的“当前事实”还说正式应用仍是 Legacy Application Library、下一步是 #12–#15；正式 Main 已接 Active Library。[S13, S20]
- `docs/REHOST.md` 顶部默认克隆旧完整分支；当前本机为 Windows 分支的新提交。旧远程分支可以保留作历史，但要说明本机新提交未必已推送，不自动发布或换分支。[S09–S11, E01]
- `ai-gateway/README` 仍引用 `.ai-run/LATEST.json`；当前 Windows 最新双客户端证据在 `.scratch` 与 repo 文档中。[S27–S29]

**建议：**只设一份精简的当前状态投影，其余入口引用它。历史内容保留但标注 `historicalAsOf`，不要同时自称 current。AGENTS 保持稳定不变量，TASK 保持当前批次，不把 5,718 行 CONTEXT 和 696 行 TASK当每次必读。详见 [治理调整提案](04-GOVERNANCE-ADJUSTMENTS.md)。

### F06｜原愿景中的 AI 主线正在被基础设施优先级稀释

**优先级：P2（路线调整），不是未经授权新增功能的指控。**

生产 B01 仍 plan-only，后台 OCR `qualify` 只有合成分支返回真资格，正常分支为 null。独立 caption、生产三能力后台执行、设备级预算和模型大小切换均没有在当前正式链路闭环。[S20, S25–S27]

同时，旧的 Platform AI Branch 状态继续有提取和测试工作；其 README 明确 32 个旧 Runtime/branch/probe/Llama 通道仍禁用。提取本身不必回滚，但不能把它作为当前模型可用性的增量成果。[S29]

**建议：**只保留必要的兼容维护，不再优先扩充没有正式消费者的诊断/安装/发布框架。任何新抽象必须说明：被哪条当期用户任务调用、替换什么重复代码、如何减少实际失败或运行成本。完成最小 Windows 收敛后，恢复原 DP02/DP03/DP04/DP05 的纵向交付。

### F07｜有诚实的失败记录，但缺一个容易执行的失败收敛队列

**优先级：P2。证据：已有报告，未独立重跑全部。**

历史 f44 完整 selected suite 有 113/135 文件 PASS、22 FAIL，另有 28 syntax-only；部分失败另有正确 runner 通过的补证，但不能机械将22减去若干得出本次最终失败数。最终 f8e 仅新增/重跑7个受影响文件，不能代表完整 suite 重新通过。[S08, S37]

**建议：**每个失败行给出当前候选、用户影响、根因类别、正式负责人、是否阻塞具体交付门、下一条可执行命令。区分产品错误、平台未支持、依赖/分发缺失、测试 runner 错误、旧断言、视觉真差异、源身份不匹配。不能仅写“历史失败，忽略”，也不要每次对所有旧失败重跑一整套。

### F08｜代码量与文档量需要按责任优化，不按文件数量裁剪

**优先级：P2/P3。证据：限定静态分析与体量统计。**

634 个 `src` TS/JS 文件中，选定五个产品入口按静态导入（包括类型）到达383个；另有251个未达，其中62个没有源内静态 importer。CLI、测试、原型 golden、运行时字符串加载及副作用并未全部纳入，因此**251/62都不是删除数量**。[E05]

部分未达簇是当前休眠 bootstrap、runtime、runtime-package、doctor、旧 IPC 和遗留 Renderer 配置；另有 packaging 和测试工具，本来就不应该由产品入口导入。

**建议：**把文件分为正式生产、受限/禁用兼容、开发测试、历史设计四种所有权。先退出生产挂载和副作用，再决定迁移/归档/删除。禁止删除实际 OCR Python、Active Library、用户修订、回执、原生工作集和安全拒绝，仅为了减少行数。旧2行路由壳无需强删；当前大文件优先拆出清楚的所有者而非机械拆成更多小文件。

### F09｜构建身份应说明覆盖范围，不冒充完整执行来源

**优先级：P2/P3。证据：构建脚本。**

当前 build ID主要覆盖 `src` 中指定扩展名和列出的 Pi/包配置。它不是所有执行资源的全集；例如独立 Python 资源不在该 walk 范围，Renderer HTML 与部分编译配置也没有作为完整 artifact closure 全量描述。[S31–S33]

其他 Runtime 自己可能另有来源校验，不能因此断言所有执行不可追溯。建议区分 source tree、应用构建、平台 Runtime、模型/配方、实际请求证据；About显示应用 build，执行详情显示实际模型/Runtime，不要求一个 hash承担所有语义。

## 6. 项目约束：应该保留什么、调整什么

### 必须保留

单一写入权威；Original/Preview/Variant；用户编辑优先；资料库代际和客户端角色；配置不等于外发许可；不静默 fallback；UNKNOWN 不提前释放；显式升级与恢复；WIP保护；普通入口与CU证据；真实模型和合成响应区别。[S01, S07]

### 应纠正而不是继续加码

- 根文档关于“Python负责所有推理”“Electron poller是唯一结果路径”的绝对句，应限定旧链路；新Pi/专用OCR各自执行，Host权威不变。

- 不能把所有异常都当作资源全局不可信；F01说明过度失败传播会直接破坏产品可用性。
- 不能用切片/严格证据持续延后普通用户结果；每批应有一个用户可验证终点。
- 不能为了“上下文预算通过”机械拆README却保留重复事实源；当前状态应统一生成/引用。
- 不能为了“独立审查”把某模型或子Agent名字写成不可替换的平台依赖；保留用户当前工具偏好及已批准的替代规则，实际执行者如实记录。
