建议采用“版本化公共能力契约 + MCP 适配器 + 隔离插件运行时”，先选少量真实插件验证移植。

当前仓库已有明确方向：

- `docs/subsystems/README.md` 已将插件、SDK、MCP 路由至 `optional-targets.md`。
- ADR 0484 是现行边界：公共能力契约、MCP 工具/资源适配、插件运行时分别负责不同问题；目前没有因该 ADR 而交付公共 API 或 MCP 服务。
- 现有 `WorkspaceClient`、内部 IPC、loopback HTTP 是正式客户端通道，不宜直接公开成插件 SDK。源码的 `WorkspaceTransport.invoke(channel, ...args)` 本身也不是稳定的领域协议。

“通用协议”需要区分两层：MCP 可作为跨软件工具/资源接入候选；它不能让依赖其他宿主私有 API、UI 和权限模型的插件原封不动运行。真正降低移植成本的是稳定的数据结构、能力发现、版本协商、错误/取消语义与宿主适配层。

建议首期只做一个明确纵切，例如分析提供者或命令插件：

1. Host 发布有类型、版本化的素材只读投影和结果提案能力。
2. 插件通过适配器接入，获得限时、限素材、限字段的句柄。
3. 插件返回提案，Host 校验、事务保存并保留来源。
4. 第三方代码独立隔离运行；不得直接写库、访问任意路径或调用私有 IPC。
5. 撤权、超时、取消、崩溃不影响已保存的用户资料；卸载不删除既有结果。

与既有决定的关系：这是 ADR 0484 已预留方向的具体化，不需要重新冻结七个贡献面或引入市场、计费、云开发平台。若选择 MCP，实施前再核对正式协议版本与传输；本次按要求未联网，未验证最新协议。
