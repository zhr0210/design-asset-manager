不能直接把主窗口的 `WorkspaceClient` 交给插件。当前它是内部接口，包含资料库、设置、AI后端及Runtime安装/启动等广泛权限；不是公开SDK。插件应经版本化、按能力收窄的契约调用，由Host统一执行身份、权限、库/输入版本、资源和结果校验。

建议首个闭环只选择一个命名能力：

- 读取素材：提供允许字段的元数据投影、不可透明解析的预览句柄；禁止原件路径、SQLite、私有IPC和主窗口Store。
- 写入素材：插件提交派生素材、分析结果或导出提案，经Host验证、必要审查及事务提交，再回读确认。不能覆盖原件或人工编辑。
- 调用AI：通过Host受限能力绑定使用既定模型/服务，约束外发目的地、费用、并发、取消和结果大小；不提供凭据和模型缓存。插件包、模型制品、可执行Runtime分别管理。
- 执行隔离：第三方代码不进入Main、主Renderer、Preload或可信Extension Host。独立进程仍须证明文件、网络、进程、资源和崩溃隔离；缺证据即不可用。

安装/更新需要校验来源、包身份、兼容性、完整权限及依赖计划，暂存后原子登记，失败保留旧版本。安装、激活、能力就绪、信任分别建模；权限扩大必须展示差异并重新授权，安装不自动意味着允许运行、下载模型或外发素材。

卸载前应展示反向依赖影响、在途任务、替代能力和存储影响；随后阻止新调用，取消/收敛任务并等待实际终态，撤销句柄、能力注册和UI贡献，清理操作暂存及可删缓存。保留已收录素材、既有结果、来源记录和用户创作数据；删除用户数据需要明确意图，不级联卸载依赖方。取消/超时不能冒充进程退出或远端零费用。

上述是目标架构，**公共SDK、安装器、隔离运行时和MCP互通尚未交付**。建议实施验收覆盖真实插件的发现→授权→隔离执行→结果审查→Host保存回读，以及撤权、崩溃、超时、更新回滚、卸载保护。
